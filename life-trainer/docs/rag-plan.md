## 0. 지금 상태 — 가장 큰 손실은 임베딩이 없는 게 아니다

```
doc            2,586건   (RSS·arXiv, 1시간마다 수집)
doc_fts        title · abstract · summary  ← summary 컬럼이 **이미 있다**
interest       30개 낱말 + 가중치, 스코어링 2,000건 완료
summary        0건       ← ★
doc_tag        LLM 태그 0건
job            reminder 3건이 전부
```

**`summarize_doc` 핸들러는 08-16 에 만들어져 있는데 큐에 넣는 곳이 없다.**
`enqueue()` 호출부가 온 저장소에 `llm/tools.py` 한 곳(예약 알림)뿐이다.
GPU 워커가 설치 이후 실질적으로 놀고 있었다.

그래서 `search_docs` 는 **제목만** 보고 답한다. 초록은 FTS 색인에 들어가 있지만
LLM 이 읽는 툴 결과에는 제목·점수·URL 만 실린다.

> 이건 "RAG 가 없다"가 아니라 **"만들어 둔 파이프라인을 안 돌리고 있다"** 는 문제다.
> 임베딩을 얹기 전에 이것부터 돌려야 비교 기준이 생긴다.

## 2. 1단계 — 야간 요약 배치

### 무엇을 넣나

```sql
SELECT id FROM doc
WHERE summary IS NULL AND state = 'scored' AND dup_of IS NULL
ORDER BY score DESC
LIMIT :n
```

점수(관심사 가중치) 상위부터. 전부 요약하지 않는다 — 2,586건 × 20초 = 14시간이다.

### 비용 (실측 기반 추정)

```
초록 ~500토큰 프롬프트 처리   ≈ 2초   (295 tok/s)
한국어 3~4문장 ~150토큰 생성  ≈ 18초  (8~9 tok/s)
─────────────────────────────────────
1건 약 20초 · 20건이면 약 7분
```

### 언제

`lifetrainer-nightly.timer` 를 새로 만든다 (**02:00**). 사용자가 자는 시간이고,
`lifetrainer-daily`(23:34)·`digest`(07:33)와 겹치지 않는다.

큐에 넣기만 하고 처리는 **기존 상시 워커**가 한다 — 워커는 이미 5초마다 폴링하고
`fcntl.flock` 으로 GPU 단일 접근을 보장한다. 새 프로세스를 띄우지 않는다.

### 함께 넣을 것

같은 배치에 `tag_activity` 도 넣는다. `unclassified` 상위 20개를 한 번의 호출로
묶어 태깅한다(핸들러는 이미 배치 처리한다). 지금 미분류 1위가 VALORANT 인데
**당시** 규칙에 게임이 하나도 없다 — LLM 태깅이 규칙 보강의 후보 목록이 된다.
(★ 이 계획대로 됐다: 게임 카테고리가 08-19 에 들어갔고, 규칙은 현재 40개다.)

## 3. 2단계 — 요약을 검색 결과에 싣기

`doc_fts` 에 `summary` 컬럼이 **이미 있다.** 스키마 변경이 필요 없다.
`search_docs` 결과 문자열에 요약 한 줄을 덧붙이면 된다.

```
현재:  제목 (점수 5.2, URL)
이후:  제목 (점수 5.2, URL) — 요약 첫 문장
```

**주의: 툴 결과 길이가 곧 다음 턴의 입력이다.** 3건 × 요약 2줄이면 300토큰이
늘고 그만큼 느려진다. 요약은 **첫 문장만** 싣고, 전문이 필요하면 모델이
`fetch_url` 로 원문을 열게 한다.

## 4. 3단계 — 대화 우선권 (배치를 켜면 반드시 필요)

지금 구조:

```
GPU 락(fcntl.flock)   worker.py 에서만 사용  ← 워커끼리만 막는다
대화 경로              락을 안 잡고 llama-server 를 직접 친다
llama-server           --parallel 1  → 요청을 한 줄로 세운다
```

야간 배치가 도는 중에 Slack 에서 질문하면 **진행 중인 요약 1건(약 20초)이 끝날
때까지 기다린다.** 평소 2초짜리 질문이 22초가 된다.

### 설계

대화가 시작되면 워커가 **다음 잡을 집지 않게** 한다. 워커는 어차피 한 번에 한 건만
처리하므로, 이것만으로 최악 대기가 20초 → 0초가 된다.

```
data/interactive.lock      대화 턴 동안 공유 락
worker._process_ready_jobs 잡을 claim 하기 전에 확인, 잡혀 있으면 이번 바퀴는 쉼
```

기존 `fcntl.flock` 관용구를 그대로 쓴다. 새 개념을 도입하지 않는다.

> 배치 시간대(02:00~05:00)를 자는 시간으로 잡는 것과 **둘 다** 한다.
> 시간대만 믿으면 새벽에 쓰는 날 그대로 걸린다.

## 5. 4단계 — 임베딩 (조건부)

### 먼저 재야 할 것

1~3 이 돌고 나서, 같은 질문 20개로 **FTS5 vs 임베딩** 검색 품질을 비교한다.
비교 없이 임베딩을 얹으면 "느려지기만 한 RAG" 가 된다.

### 붙인다면

| 항목 | 선택 | 이유 |
|---|---|---|
| 모델 | `bge-m3` 계열 int8, **CPU** | 음성 스택에서 sherpa-onnx 가 **GPU 를 전혀 안 쓰고** ASR RTF 0.042 를 냈다. GPU 는 llama-server 가 8.6GB 로 이미 꽉 찼다 |
| 저장 | `doc_vec(doc_id, vec BLOB)` + numpy | 2,586건 × 1024차원 float16 ≈ 5MB. **brute-force 로 충분하다.** sqlite-vec 같은 새 확장을 들이지 않는다 |
| 검색 | 하이브리드 (FTS5 상위 N ∪ 벡터 상위 N → 재순위) | FTS5 는 고유명사·정확 일치에 강하고 벡터는 의미에 강하다. 둘 다 쓴다 |
| 대상 | **초록**만 | 청킹 없이 문서 1건 = 벡터 1개. arXiv 초록은 원래 짧다 |

배치 비용: 2,586건 CPU 임베딩은 몇 시간짜리다. 야간 배치에 얹어 며칠에 걸쳐 채운다.

### 실측 후기 (2026-08-23 오후) — 20질의 비교를 건너뛴 대가

붙이고 나서 8질의로 재봤다. **RRF 의 이득은 두 목록이 겹칠 때** 나온다(양쪽에서
발견된 문서가 점수를 두 번 받는다). 그런데:

```
질의 8개 · 풀 20+20 · 총 겹침 4건 (약 1%)
최종 상위3 출처:  K V K / K V K / B K V / K V K / K V K / B B K / K V K / B V K
```

`vector_weight=0.5` 에서 키워드 1위와 벡터 1위 점수가 `0.5/60` 으로 **정확히 동점**이라
융합이 **지퍼(1:1 교대)** 가 된다. 즉 모델에게 주는 3칸 중 **1칸이 벡터 몫으로 고정
배정**되고, 그 문서가 무관해도 들어간다 (`jetson` 질의에 Google Antigravity 가 2번).

코사인 점수가 변별을 못 한다 — `jetson` 질의에서 상위 20위 점수폭이 0.699~0.647 이다.

원인 후보 둘:
1. **Qwen3-Embedding 의 instruct 접두 미사용.** 질의에 `Instruct: ...\nQuery:` 를 붙이는
   것을 전제로 학습된 모델인데 맨 질의를 보낸다. 붙여서 재보니 `jetson` 이
   `Google Antigravity` → `Jetson Orin NX / jetson orin nano` 로 뒤집혔다.
   다만 한국어 개념 질의("온디바이스 추론 최적화")는 접두로도 안 나아졌다
2. **코사인 컷오프 없음.** 벡터 쪽은 항상 상위 N 을 내놓는다. 무관해도 순위는 매겨진다

### 20질의 비교 결과 (2026-08-23 저녁) — 빚을 갚았다

`scripts/eval_search.py` 로 잰다(재실행 가능). 엔티티 10질의는 **정답이 기계로
판정된다** — 찾는 낱말이 제목·초록에 있으면 관련이다.

```
                    kw     vec   vec+i     rrf   rrf+i
hit@5              96%     44%     86%     76%     98%
                                            ↑
                          ★ 현재 하이브리드가 키워드 단독보다 나빴다
```

**§5 가 경고한 "느려지기만 한 RAG" 가 실제로 그랬다.** 벡터를 섞은 것이 순손해였고,
비교를 건너뛰었기 때문에 두 달 가까이 아무도 몰랐다.

`vector_weight` 를 바꿔도 원인이 안 없어진다:

```
weight       0.3    0.5    0.7
rrf          96%    76%    50%     ← 접두 없음: 벡터를 덜 섞을수록 낫다(=벡터가 해롭다)
rrf+i        98%    98%    96%     ← 접두 있음: 어느 값이든 안정
```

**결정 셋:**

1. **instruct 접두를 붙인다** (`embed.query_instruct`). 질의에만, 문서에는 안 붙인다.
   문서 벡터가 안 바뀌므로 **재색인이 필요 없다.**
2. **`vector_weight` 는 0.5 유지.** 접두 적용 후 0.3 과 동률(98%)이라 두 변수를
   같이 바꿀 이유가 없다.
3. **코사인 컷오프는 안 붙인다.** 개념 질의 10개의 1위 점수가 0.50~0.65 로 흩어져
   **절대 컷오프가 성립하지 않는다** — 0.55 로 자르면 어떤 질의는 전멸하고 어떤
   질의는 하나도 안 잘린다. 접두만으로 98% 면 복잡도를 더할 이유가 없다.

## 6. 5단계 — 청킹 (하지 않기로 함)

현재 검색 대상은 **제목 + 초록 + 요약**이라 문서 하나가 이미 청크 하나 크기다.
본문을 활용하려면 청킹이 필요하지만, 본문 활용 자체를 범위에서 제외했다.

### 2026-09-04 — 본문 수집 실험

§7 이 *"초록으로 부족하다는 증거가 나오면 그때"* 라고 적어 뒀다. 재 봤다.

**검색은 병목이 아니다.** 엔티티 질의 10개에서 하이브리드+접두가 `hit@5` 100% 다
(`scripts/eval_search.py`). 못 찾는 게 아니라 **찾은 문서 안에 내용이 없는** 것이고,
그건 소스마다 갈린다 — arXiv 초록은 1,400자대인데 뉴스 피드는 157~322자다.
전체의 29% 가 300자 미만, 한 문단도 안 된다.

그래서 **짧은 초록만** 전문을 받는 수동 실험 경로를 만들었다
(`collect/bodies.py` · `lt bodies --limit N`).
전부 받는 것은 여전히 안 한다 — arXiv 까지 받으면 얻는 것 없이 robots·용량·요약
비용만 는다. **§7 을 뒤집은 게 아니라 그 조건절을 실행한 것이다.**

> **2026-09-09 결정:** 본문 활용과 청킹을 더 진행하지 않는다. Phase 4는 제목·초록·
> 요약을 대상으로 야간 요약, 검색 결과 요약, 임베딩+하이브리드 검색이 동작하는
> 1~4단계에서 완료로 닫는다. 실험용 본문 수집 명령은 남기지만 자동화·요약 연결·
> 청킹은 범위 밖이다.

## 8. 이 설계가 지키는 것

- ~~**새 상주 프로세스 0개**~~ — ✗ **깨졌다.** 4단계에서 `llama-embed.service`(1.8GB)가
  늘었다. §7 에서 "상주 프로세스를 하나 더 띄우는 것은 메모리 예산에 맞지 않는다"고
  써 놓고 벡터 DB 가 아닌 임베딩 서버라는 형태로 결국 하나를 띄웠다.
  대가는 스왑 2.4GB 였고, 08-23 ctx 축소(2.99GB → 1.50GB)로 갚았다
- **새 테이블 최소** — ✓ `doc_fts.summary` 는 이미 있었고 4단계에서 `doc_embedding` 하나
- **측정 후 결정** — ✗ 건너뛰었다가 **2026-08-23 저녁에 갚았다.** 20질의 비교를
  `scripts/eval_search.py` 로 돌렸고, 하이브리드(76%)가 키워드 단독(96%)보다 나쁘다는
  것이 드러났다. instruct 접두로 98% 로 올렸다 (§5 「20질의 비교 결과」).
  **건너뛴 대가가 정확히 §5 가 경고한 "느려지기만 한 RAG" 였다**
- **대화가 배치에 밀리지 않는다** — ✓ 3단계 `interactive.lock` 으로 성립
