## 무엇이 문제인가

겹치는 이벤트를 제거하는 로직에 구멍이 있고, 걸리면 결과가 `away`(자리비움) 쪽으로
기운다. **활동을 과소 계상하는 방향이라 조용히 부풀리지는 않는다** — 그래서 급하지 않다.

## ★ 2026-09-03 실측 — 올렸다가 되돌렸다

**올릴 때 근거는 "밤 afk 8시간이 사라진다"였다. 그건 재고 한 말이 아니었다.**
롤업을 실제로 돌려 비교하니 화면에 보이는 것은 **아무것도 안 바뀐다.**

같은 상태를 합치도록 고친 판으로 09-02 를 다시 롤업한 결과:

```
                밤 36슬롯       afk      gap    카테고리
① 지금                        5.59h    0.00h   off 33 · ent 1 · browsing 1 · away 1
② 폰 afk 를 지우면              0.01h    5.59h   ← 카테고리 완전히 동일
③ 폰 없음 + 고친 판             5.59h    0.00h   ← 카테고리 완전히 동일
```

★ **격자·카테고리는 세 경우가 같다.** 밤은 어느 쪽이든 `off` 다.
바뀌는 것은 `afk_sec` 라는 내부 숫자뿐이고, 그것도 폰이 없을 때만이다.
`afk_sec` 는 일일 리포트의 "자리비움" 필드에만 실린다.

## 원래 기제 (그대로 남는다)

같은 상태(`afk`)끼리도 서로를 자른다. 상류가 같은 시작(0.4ms 안)으로 118건을
발행한 밤에, **PC 의 afk 490.5분이 정규화 뒤 35.9분이 됐다:**

```
정규화 전   00:07:41.159 → 08:18:10.128   490.5분  (그 외 117건이 같은 시작)
정규화 후   00:07:41     → 00:13:48         6.1분  + 0.0분짜리 슬리버 117개
```

기제: `_dedupe_overlaps` 는 `(ts, ts_end)` 로 정렬한 뒤 **각 이벤트를 다음 이벤트의
시작으로 자른다.** 시작이 0.4ms 안에 몰려 있으면 앞의 117개가 전부 슬리버가 되고,
가장 늦게 시작한 것 하나만 살아남는다 — 그런데 그것이 **가장 짧은 것**이었다.

### 폰이 같은 밤을 덮고 있다

같은 밤을 폰의 afk 워처가 364.5분짜리 이벤트 하나로 정확히 덮었다. 기기 중재가
PC 를 "데이터 없음"으로 보고 폰을 택한다. 폰이 없으면 `afk_sec` 가 `gap_sec` 로
옮겨가지만 **카테고리는 그대로 `off`** 다 (위 실측 ②).

### 고칠 방향

같은 상태끼리는 **자르지 말고 합쳐야 한다.** 한 버킷에서 겹치는 `afk` 두 개는
상태 전환이 아니라 같은 상태의 중복 관측이다. 자르는 것이 옳은 경우는
**상태가 다를 때**뿐이다(`afk` → `not-afk`).

```
지금:  같은 상태끼리도 뒤가 앞을 자른다        → 슬리버 117개 + 6.1분
제안:  같은 상태는 union, 다른 상태만 자른다   → 490.5분 하나
```

★ 고치기 전에 [`0027` 의 기록](../../HISTORY/2026-09-07-a-clock-that-drifted-backwards-made-one-event-into-many.md) 을 같이 볼 것.
상류가 왜 118건을 발행하는지(aw-server v0.13.2 자체 비율 152.25)를 모른 채 정규화만
바꾸면 다른 쪽이 깨진다 — 아래 §같이 봐야 하는 것과 같은 이유다.

★ **전제가 하나 바뀌었다 (2026-09-07).** `upsert_events` 가 이제 *같은 내용 · 겹침* 인
중복 발행을 저장 단계에서 흡수한다. 즉 여기 적힌 "118건" 은 **상류의 숫자**이고,
우리 표에는 그만큼 안 들어온다. 다시 잴 때는 사본에서 `lt --dev` 로 확인할 것.
