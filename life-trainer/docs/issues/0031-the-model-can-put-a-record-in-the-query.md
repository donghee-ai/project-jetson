# 모델이 기록에서 뽑은 낱말을 검색어에 넣을 수 있다

- **상태**: 열림. 고칠 수 있는 문제지만 안전한 대조 기준과 오탐 수치를 아직 정하지 못했다
- **발견**: 2026-09-08 공개 전 감사. `llm/websearch.py`의 약속을 강제하는 코드를 찾을 수 없었다
- **증상**: 모델이 계획·활동·문서 제목에서 뽑은 낱말을 외부 검색 질의에 넣을 수 있다.
  실제 발생 여부는 아직 확인하지 않았다

## 재현

```bash
cd life-trainer && .venv/bin/python - <<'EOF'
from lifetrainer.llm.trigger import is_personal
for query in ["어제 뭐 했지", "내 오늘 일정", "오늘은?"]:
    print(repr(query), is_personal(query))
for query in ["예시 학원 수강신청 기간", "On-Device Inference", "phone battery"]:
    print(repr(query), is_personal(query))
EOF
```

앞 세 줄은 `True`, 뒤 세 줄은 `False`다. 뒤의 질의는 `search()` 관문을 통과한다.

## 원인

게이트가 개인정보 자체를 판정한다고 믿었지만, 실제로 보는 것은 `내/오늘/이번 주`와
`계획/일정/할 일` 같은 **자기지칭 어형**이다. 사용자 원문을 막는 데는 유효하지만,
모델 컨텍스트에서 나온 제목에는 그 출처 표시가 남지 않는다.

```text
context.py / tools.py   계획·활동·문서 제목
          ↓
       모델이 읽고 검색어를 생성
          ↓
websearch.search()      is_personal(query) == False
          ↓
        Serper
```

검색어를 짧게 쓰라는 모델 지시는 있지만, 따르지 않았을 때 막는 장치는 없다.

## 영향과 현재 한계

- 외부 전송 대상은 Serper이며, 한 번 전송된 질의는 회수할 수 없다
- 선주입 경로는 사용자 원문과 조립 결과를 모두 검사하므로 이 문제와 범위가 다르다
- 모델 도구 호출과 MCP 경로도 `search()`로 합류해 관문의 위치는 맞지만 판정 기준이 좁다
- `search()` 발송 직전 로그가 있어 실제 발생 여부를 조사할 재료는 남는다

## 고칠 것

후보는 검색 직전에 최근 `aw_event.title`, `plan.title`, `doc.title`과 질의어를 대조하는
것이다. 다만 흔한 앱 이름까지 막는 오탐 위험이 크므로 다음 순서로 진행한다.

1. 외부 검색 로그와 최근 기록 제목을 로컬에서 대조해 실제 발생 수와 어휘를 측정한다.
2. 고유성이 충분한 토큰의 기준과 캐시 범위를 정한다.
3. 모든 호출자가 합류하는 `websearch.search()`에 관문과 회귀 테스트를 추가한다.

이번 수정은 문장을 코드에 맞게 축소한 것이다. 강제 장치를 구현한 것은 아니므로 이 이슈는
열린 상태로 둔다.
