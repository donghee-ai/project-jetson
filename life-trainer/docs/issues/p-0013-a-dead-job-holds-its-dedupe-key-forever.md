# 죽은 잡이 dedupe_key 를 영구 점유해 그 문서를 큐에서 영구 배제한다

- **번호**: `0013`
- **발견일**: 2026-08-23 (`pending-changes.md`) · **재측정 2026-08-27**
- **상태**: 🔵 **p — 지금은 피해가 없다.** 다만 구조는 그대로다

## 구조 (확인됨)

```sql
-- schema.sql:502
dedupe_key   TEXT UNIQUE
```

`queue.enqueue()` 는 *"`dedupe_key` 가 이미 존재하면 넣지 않고 `None` 을 반환한다"*.
**`state` 를 안 본다.** 그래서 `attempts` 를 소진하고 `failed` 가 된 잡도 자리를
계속 차지하고, **그 문서는 다시는 큐에 못 들어간다.**

지금 그런 잡이 203건 있다
([HISTORY 08-21](../../HISTORY/2026-08-21-a-loading-model-burned-the-whole-queue.md)).

## 원래 주장과 재측정 — 당시엔 참, 지금은 아니다

`pending-changes.md` 는 이렇게 적어 뒀다:

> *"하필 점수 상위라 매일 밤 상한 30건 중 절반 이상을 갉아먹는다
> (실측: 후보 60건 중 32건이 이것 때문에 빠졌다)"*

2026-08-27 재측정:

```
죽은 203건 평균 점수          1.32   (범위 0.9~1.81)
요약 없는 문서 전체 평균       0.77
요약 있는 문서 전체 평균       3.61

요약 없는 문서를 점수순 정렬했을 때
  상위 60건 중 죽은 잡에 묶인 것   0건
  상위 30건 중                    0건
```

문서 풀이 4,435 → 6,039 로 늘면서 **더 높은 점수의 문서가 위로 올라갔다.**
야간 예산을 갉아먹지 않는다. **주장이 틀린 게 아니라 유효기간이 지났다.**

## 그래도 남기는 이유

- **메커니즘은 그대로다.** 앞으로 어떤 잡이든 `attempts` 를 소진하면 그 문서는
  영구 배제된다. 그리고 **에러가 안 난다** — 조용히 빠진다
- **`lt score` 를 다시 돌릴 계획이 있다**(관심사 확대, HANDOFF §7-C). 점수가
  오르면 이 203건이 상위로 올라올 수 있는데 **그때도 못 들어간다**

## 고칠 것

`dedupe_key` 를 "큐에 있는 동안"만 유효하게 만든다 — 종료 상태(`done`/`failed`)로
갈 때 `NULL` 로 비우거나, UNIQUE 를 `(dedupe_key, state)` 가 아니라 부분 인덱스
(`WHERE state IN ('queued','running')`)로 바꾼다.

**후자가 맞아 보인다** — `done` 인 잡의 재적재도 같이 막아야 하는지는 따로 판단할 문제다.
