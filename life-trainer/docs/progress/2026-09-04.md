# 2026-09-04 — 폰 브라우징이 무엇을 봤는지 말하게 했다

## 무엇을 더했나

폰 크롬 슬롯이 전부 `"Chrome"` 이었다. 웹 버킷에는 페이지 제목과 URL 이 멀쩡히
들어와 있는데(폰 앱이 09-03 부터 채운다) 슬롯까지 오는 길이 없었다. 두 곳을 이었다.

**1. URL 게이트** — `rollup.py` 는 `if classifier.is_browser(app)` 일 때만 url 을 붙이는데
`browser_apps` 가 데스크톱 실행파일명뿐이라 `com.android.chrome` 이 못 넘었다.
안드로이드 패키지를 넣었다. 목록은 앱의 `WebWatcher.KNOWN_BROWSER_PACKAGES` 와 같게 뒀다.

**2. 표시용 제목** — `contribs` 에는 window 이벤트만 들어가고 `top_title` 은 거기서
뽑히므로 웹 제목이 닿을 길이 없었다. 브라우저 세션일 때 겹침이 가장 큰 웹 이벤트의
제목을 표시용으로 쓴다.

```
2026-09-03 16:10   Chrome  →  게시글 제목 - 인기글 목록 - 예시 커뮤니티
2026-09-03 12:40   Chrome  →  rag 임베딩이란 - Google 검색
2026-09-04 09:10   Chrome  →  리얼센스 디벨로퍼 - Google 검색
```

## ★ 분류에는 안 넣었다

`title` 을 바꾸면 제목 규칙이 다르게 걸려 카테고리가 움직이고, 그러면 **집계 원천인
`slot_breakdown` 이 바뀐다.** 이 변경은 시각화 층만 건드리는 것으로 뒀다 — 페이지 제목을
분류에 먹이는 것은 값이 있어 보이지만 따로 재고 정할 일이다.

경계를 지키는 테스트를 같이 뒀다: 웹 제목이 있을 때와 없을 때의 `slot_breakdown` 이
같아야 한다. 깨지면 제목이 분류로 샌 것이다.

`_best_web_url` 은 `_best_web(..., field)` 로 일반화했다. url 과 title 이 각자 겹침
계산을 하면 같은 값을 두 곳에서 따로 세는 것이 된다.

## ★ URL 은 뚫렸지만 흘릴 것이 없다

재롤업 전후 카테고리 합이 거의 같다 (엔터테인먼트 +0.2분). URL 규칙이 이 사람이 실제로
보는 사이트를 하나도 안 덮기 때문이다:

```
실제:  m.example-forum.com · m.example-board.com · m.example-portal.com · example-stream.com · example-blog.net · google 검색
규칙:  arxiv · github · mail · op.gg/inven · youtube · 뉴스사이트
```

움직인 0.2분이 `youtube.com` 규칙이 걸린 것이고 그게 배관이 뚫렸다는 증거다.
**규칙을 늘릴지는 "이 시간을 무엇으로 셀 것인가"라는 사람의 결정**이라 여기서 안 했다.

## 곁가지 — 폰이 주소창 힌트를 URL 로 보낸다

재다가 나왔다. `"Google 검색 또는 URL 입력"` 이 url 자리에 **128회 13.8분** 들어와 있다.
주소창이 비었을 때의 안내 문구다. 폰 `WebWatcher.extractUrl` 이 그것까지 읽는다 —
폰 쪽에서 걸러야 한다.

# 2026-09-04 (오후) — 아침에 오는 것이 어제와 같았던 이유

오전은 폰 브라우징이 무엇을 봤는지 말하게 한 것이었다 (위). 오후는 **매일 나가는데
갱신은 안 되던 것들**이다. 세 갈래인데 뿌리가 같다 — *돌고 있다*와 *값을 한다*는 다르다.

## 1. 아침 다이제스트 — 8일 연속 같은 문서

사람이 알아챘다. 원인이 둘이었고 둘 다 고쳤다. 경위는
[HISTORY](../../HISTORY/2026-09-04-the-decay-was-frozen-into-the-score.md) 에 있다.
요지만: **최신성 보정이 채점 시점에 굳어 있었고**(있는데 한 번만 적용됐다),
**보낸 문서를 거를 자리가 없었다.**

구조가 바뀐 지점 하나만 여기 남긴다 — **`doc.score` 의 뜻이 바뀌었다.**

| | 전 | 후 |
|---|---|---|
| `doc.score` | 관심사 매칭 × 최신성 (**저장 시점에 굳음**) | 관심사 매칭만. **시간이 안 들어간다** |
| 랭킹 | 저장된 값 그대로 | `score × 최신성(지금)` — `top_docs` 가 읽을 때 곱한다 |

**시간이 들어간 값을 파생 컬럼에 저장하면 그건 그 순간의 사실이고 다음 날부터
틀린 사실이다.** 같은 모양이 이 저장소에 또 있는지는 아직 안 훑었다.

## 2. 워처 침묵 검사에 unlock 을 넣었다

오전에 media를 감시하게 만들었는데, **그날 unlock이 죽어 있었다**.
하나를 붙이면서 옆의 것을 안 본 것이다. 목록을 `WATCHED_PHONE_BUCKETS` 표로 뺐다 —
다음에 web 을 넣을 때는 한 줄이다.

임계값은 개인별 잠금해제 간격을 공개하지 않고, 로컬 표본에서 정상적인 밤 간격은
통과하고 실제 장기 침묵만 잡는 값으로 정했다.

## 3. RAG — §7 의 조건절이 발동했다

[rag-plan §7](../rag-plan.md) 이 **전문 수집을 안 하기로** 하면서 조건을 달아 뒀다:
*"초록으로 부족하다는 증거가 나오면 그때."* 재 봤다.

- **검색은 병목이 아니다** — 엔티티 질의 하이브리드+접두 `hit@5` 100% (`scripts/eval_search.py`)
- **모자란 건 찾은 문서 안의 내용**이고 소스마다 갈린다 — arXiv 초록은 1,400자대,
  뉴스 피드는 157~322자. 전체의 29% 가 300자 미만

그래서 **짧은 초록만** 받는다 (`collect/bodies.py` · `lt bodies --limit N`).
전부 받는 것은 그대로 안 한다 — §7 을 뒤집은 게 아니라 조건절을 실행한 것이다.

> ★ **재료만 있고 읽는 곳이 없다.** `body_path` 가 채워져도 검색·요약·임베딩은 여전히
> 제목·초록·요약만 본다. **다음 삽은 야간 요약이 본문을 읽게 하는 것**이다 —
> 요약은 이미 FTS 와 다이제스트에 실리므로 청킹보다 먼저 값이 나온다.
> **타이머도 안 붙였다.** 값을 한다는 걸 보기 전에 자동으로 돌리면 확인할 기회가 사라진다.

## 곁가지 — schema.sql 은 마이그레이션보다 먼저 부어진다

`digested_at` 에 인덱스를 달고 `schema.sql` 에도 적었더니 **`lt backup` 이 즉시 죽었다.**
`open_db` 가 `init_db`(schema.sql) → `migrate()` 순서라, 옛 DB 에는 아직 없는 컬럼을
참조하는 인덱스 한 줄이 schema.sql 전체를 깬다. 006 은 컬럼만 더해서 안 밟았다.

**마이그레이션이 더한 컬럼을 참조하는 인덱스를 `schema.sql` 에 두면 안 된다.**
008·009 머리말에 적어 뒀다.

## 4. 곁가지가 하나 더 — 버전 도장을 두 프로세스가 서로 되돌렸다

008·009 를 적용했는데 `make status` 가 `v7` 이라 했다. `init_db` 가 `open_db` 마다
**자기 프로세스의 상수로** meta 를 갈아엎고 있었고, 나흘째 떠 있는 web·worker·slack 이
7 을 들고 있었다. 게다가 `migrate()` 의 도장이 `if applied:` 안이라 **되돌아간 것을
고칠 방법이 없었다.** 경위는
[HISTORY](../../HISTORY/2026-09-04-the-version-stamp-two-processes-fought-over.md).

★ **아직 안 꺼졌다.** 되돌리는 쪽이 옛 코드로 돌고 있다:

```bash
systemctl --user restart lifetrainer-web lifetrainer-worker lifetrainer-slack
```

## 5. `/private` 슬래시 명령 — 그리고 예산이 그것을 막아섰다

*"에이전트가 프라이빗을 켤 수 있나"* 에서 시작했다. 답은 **아니오** 였다 — 툴 9개에도,
`slash` 가 부를 수 있는 명령 10개에도 없었다.

**에이전트 툴이 아니라 슬래시로 붙였다.** 모델은 명령 문자열만 고르고 실제 동작은 코드가
한다 — 8B 가 툴을 안 부르고 *"껐습니다"* 로 끝내는 실패 모드가 **구조적으로 불가능**하다.
다른 명령이면 답이 틀리고 말지만 **프라이빗은 사람이 켜졌다고 믿고 행동한다.**
결과적으로 에이전트도 `slash` 로 부를 수 있으니 원래 질문도 같이 풀렸다.

답에는 항상 결과 상태를 담는다 — *"켰습니다"* 가 아니라 `프라이빗: 켜짐 — 30분 남음`.
요청과 결과가 어긋나면 사람 눈에 보여야 한다.

### 예산이 강제한 대화

명령 하나를 더하자 `TOOL_TOKEN_BUDGET` 이 **3,037/3,000** 으로 넘어갔다. 그 상수가
*"툴을 더 붙이고 싶으면 무엇을 뺄지 먼저 정한다"* 는 대화를 강제하려고 있는 것이고,
실제로 강제됐다. 다섯 곳을 줄여 **2,992** 로 넣었다.

★ 그중 하나는 **중복이었다** — `/done` 의 `(예: /done 미팅)` 이 툴 설명 머리말의
*"계획은 제목으로 지목한다"* 예시와 같은 글자였다. 같은 예시를 매 턴 두 번 싣고 있었다.
**예산이 없었으면 안 찾았을 것이다.**

## 6. PC 프라이빗 헬퍼 — 안 만들기로

**폰은 우리가 만든 앱이고 노트북은 순정 ActivityWatch 다.** 순정 프로그램을 밖에서
조종하는 스크립트는 업데이트마다 조용히 깨지고, **깨진 상태가 곧 프라이버시가 안 걸린
상태**다 — 실패 방향이 나쁜 쪽이다.

젯슨 DB 는 헬퍼 없이도 안 샌다(저장 관문). 받아들인 것은 **PC 로컬 AW DB 에는 남는다**
는 것뿐이고, 정리는 `lt private purge --minutes N --aw`.
결정과 되살릴 조건은 [`for_window/01`](../../../for_window/01-private-mode-pc-helper.md).
실측 3가지(워처 인자·aw-qt 부활·재개 시 backfill)는 **안 재기로 했다.**
