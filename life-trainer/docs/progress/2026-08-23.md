### 왜 벡터 인덱스를 안 썼나

4천 건 × 1024차원 = 16MB 다. numpy 로 전수 내적이 밀리초다.
`sqlite-vec` 같은 새 의존성은 **10만 건을 넘길 때** 고민한다 — 지금 얹으면 비교 기준이 없다.

### 왜 요약이 붙으면 다시 임베딩하나

임베딩 원문이 `title + abstract + summary` 라 요약이 나중에 채워지면 원문이 바뀐다.
`source_hash` 로 그것을 감지한다. **처음 구현은 SQL 이 해시를 안 봤다** — 그대로 뒀으면
야간 요약이 붙은 문서가 옛 벡터를 달고 있어 검색이 요약을 영영 못 봤을 것이다.

## 실측으로 잡은 것 셋

**① 슬롯당 컨텍스트** — `-c 2048 --parallel 4` 로 뒀더니 슬롯당 512 토큰이 되어,
1600자(≈800토큰)짜리 문서 **하나조차** 거부됐다(`exceeds the available context size`).
`-c` 는 슬롯 전체 합이다. → `-c 8192 --parallel 4` = 슬롯당 2048.

**② OOM** — 여유가 있다고 `-c 16384 -b 16384` 로 키웠더니 유닛의 `MemoryMax=2G` 에 걸려
`oom-kill` 로 죽었다. 실측 상주 1.6GB 에 맞춰 3G 로 올리고 크기를 되돌렸다.

**③ 8B 가 다시 안 올라왔다 ★ 가장 컸다** — 임베딩 서버를 GPU(`-ngl 99`)에 올렸더니
상주가 **3,144MB** 로 불어(모델 파일은 610MB) 8B 가 CUDA 버퍼 4.67GB 를 못 잡고 기동에
실패했다. 컨텍스트·계산 버퍼가 모델 크기만큼 더 붙는다.

> **깨진 가정: "0.6B 는 610MB 니 8B 옆에 그냥 든다."** 파일 크기는 상주 메모리가 아니다.
> `-ngl 0` 으로 CPU 에 내리고 `-c 4096 --parallel 2` 로 줄여 **1,893MB**. 8B 가 이 기기의
> 주인공이므로 임베딩이 양보한다. CPU 실측: 질의 1건 **499ms**, 4건 배치 **1,770ms** —
> 대화 한 턴이 2~3초인 것에 비하면 감당된다.

**④ 마크업 유출** — 요약에 `<ul><li><strong>` 이 그대로 들어 있었다. 툴 결과에 실리면
토큰을 태그가 먹고 8B 가 태그를 따라 쓴다. `_plain()` 으로 걷어낸다.

## 오후 — KV 캐시를 절반으로 줄여 4.4GB 를 되찾았다

아침에 임베딩 서버를 들이면서 메모리가 바닥났다. `free` 를 보니 **가용 200MB, 스왑 3,890MB**
였고 8B 자신이 1,164MB 스왑아웃 상태였다. 임베딩 서버는 2,469MB 가 스왑에 나가 있었다.

### 왜 컨텍스트였나 — 계산부터 했다

GGUF 메타데이터에서 직접 셌다 (36층 · KV헤드 8 · head_dim 128, `-ctk/-ctv q8_0`):

```
토큰당 KV = 36 × 8 × (128+128) × 1.0625 = 76.5 KiB
n_ctx 40,960 → KV 2.99 GB
```

모델 4.68GB + KV 2.99GB + CUDA/계산버퍼 1.2GB = **8.87GB**. 관측된 유휴 RSS 가 8.9GB 인데
그때 슬롯은 `n_past=0` — **빈 KV 캐시가 3GB 를 이미 물고 있었다.** 지연 할당이면 유휴가
5.9GB 여야 한다. 즉 **컨텍스트는 시동 시 전액 선불이고 대화 길이와 무관하다.**

그런데 앱이 쓰는 양을 재보니:

```
시스템 프리앰블+오늘 배경  525 토큰
턴 배경(계획·활동·관심사)   96
사용자 질문                12
툴 스키마 4개             517
──────────────────────────────
1턴 최소                1,150 토큰   ·   최악(히스토리6+툴3라운드) ≈ 2,980
```

`MAX_HISTORY_MESSAGES=6` 으로 상한이 **구조적**이라 이 값이 늘어날 길이 없다.
40,960 중 7% 다. **KV 2.99GB 중 2.7GB 가 영구히 놀고 있었다.**

`-c 40960` 은 `llama-server-qwen3.sh` 주석대로 "`n_ctx_train` 상한"이라 고른 값이었다.
필요해서가 아니었다.

### 20,480 을 고른 이유

8,192 로도 앱은 돌지만, 이 서버는 **OpenClaw 와 공유**한다. OpenClaw 압축 설정
(`maxHistoryShare 0.7` + `reserveTokens 6000`)이 재계산 없이 성립하는 하한이 20,480 이다:

```
0.7 × 20,480 = 14,336  +  예약 6,000  =  20,336  <  20,480   (여유 144토큰)
```

더 낮추려면 압축 설정까지 손봐야 한다.

### 결과 — 회수분(1.49GB)보다 컸다

```
              변경 전                변경 후
가용           200 MB      →      4,566 MB
스왑         3,890 MB      →      1,474 MB
8B      RSS 9,174 / 스왑 1,164  →  RSS 6,845 / 스왑 0
임베딩   RSS 1,231 / 스왑 2,469  →  RSS 1,800 / 스왑 0
페이지캐시      302 MB      →      4,371 MB
```

세 프로세스가 스왑에서 나오고 페이지 캐시가 복구되면서 연쇄로 풀렸다.
**RAG 벡터 검색이 매 질의마다 `doc_embedding` 16.7MB 를 통째로 읽으므로**
페이지 캐시 복구가 그대로 검색 지연으로 돌아온다.

## 오후 — 하이브리드 검색을 뒤늦게 측정했다

`vector_weight = 0.5` 에 근거가 없다는 것이 아침 기록의 "남은 것" 1번이었다.
8질의로 재봤더니 **더 근본적인 게 나왔다.**

**RRF 의 이득은 두 목록이 겹칠 때** 나온다 — 양쪽에서 발견된 문서가 점수를 두 번 받아
위로 올라오는 것이 융합의 요지다. 그런데:

```

최종 상위3 출처:  K V K / K V K / B K V / K V K / K V K / B B K / K V K / B V K
```

`vector_weight=0.5` 에서 키워드 1위와 벡터 1위 점수가 `0.5/60` 으로 **정확히 동점**이다.
그래서 융합이 재순위가 아니라 **지퍼(1:1 교대)** 가 된다. 모델에게 주는 3칸 중
**1칸이 벡터 몫으로 고정 배정**되고, 그 문서가 무관해도 들어간다:

```
'jetson' 검색 결과 3건 (검색 방식: 키워드+벡터):
1. Proxmox VE on Jetson AGX Orin / Jetson Thor ...
2. Introducing Google Antigravity              ← ★ 무관한데 벡터 몫으로 들어왔다
3. Jetson AGX Thor and Orin, Hardware testing software
```

코사인이 변별을 못 한다 — `jetson` 질의에서 상위 20위 점수폭이 **0.699~0.647** 이다.

원인 하나는 찾았다: **Qwen3-Embedding 은 질의에만 `Instruct: ...\nQuery:` 접두를 붙이는
것을 전제로 학습됐는데** `embed_query()` 가 맨 질의를 보낸다. 붙여서 재보니:

```
[jetson] 현재(맨질의)              [jetson] instruct 접두
  0.698 Introducing Google Anti…    0.626 Powerful Compute So Compact — Build AI Anywhere
  0.694 Reachy Mini                 0.578 Jetson Orin NX 16GB (40W) and Orin Nano Super
```

고유명사 질의는 접두 하나로 뒤집힌다. **다만 만능이 아니다** — 한국어 개념 질의
("온디바이스 추론 최적화")는 접두를 붙여도 안 나아졌고 오히려 약간 나빠졌다.

### ① `aw-watcher-android-web` 이 `web` 이 아니라 `android` 로 잡혔다

`aw_sync.bucket_type()` 의 판별 순서가 `unlock → afk → android → web` 이라,

영원히 도달하지 못했다.** docstring 이 "순서가 곧 우선순위다"라며 `unlock` 과
`afk` 를 앞에 둔 이유를 적어놨는데 `web` 만 같은 처리를 못 받았다.

**에러는 나지 않았다.** 롤업은 URL 을 `dev.buckets["web"]` 에서만 꺼내 슬롯에
붙이는데 폰의 web 버킷이 항상 비어 있었고, `rules.yaml` 의 URL 규칙(앱 규칙보다
**먼저** 평가되도록 일부러 배치한 것)이 폰 브라우징에 하나도 걸리지 않았다.

수정은 `web` 을 `android` 위로 한 줄. 회귀 테스트 3개를 붙였다
(`test_bucket_type_android_web_is_web_not_android` 외 2개). DB 의 `aw_bucket.type`
1건을 갱신하고 08-12~08-23 을 재롤업했다. 서비스 재시작도 필요했다 —
폰 push 를 받는 `lifetrainer-web` 이 옛 코드를 메모리에 들고 있었다.

**다만 효과는 예상보다 훨씬 작았다.** 처음엔 "폰 크롬 누적분이 URL 분류를 새로
받는다"고 봤는데 틀렸다. 크롬 **사용 시간**과 web 워처가 **뽑아낸 URL** 을 같은
것으로 착각한 것이다:

```
aw-watcher-android-web 이벤트   매우 적음
폰 크롬 누적                    개인별 값 제거
재롤업 후 변화                  미미함
```

지금 이득이 아니라 **잠복 버그 제거**다. web 워처가 제대로 돌기 시작하면 그때

합성 회귀 데이터에서도 앱 세션과 media가 이중 계산되지 않았다.

남은 구멍은 **화면을 끄고 오디오만 재생하는 경우**라 별도 과제로 남겼다.

## 밤 — URL 을 주는 기기가 하나도 없다

①을 고치고 나서야 보였다. **`rules.yaml` 의 URL 규칙 6개가 지금 전부 사문이다.**

```
노트북 aw-watcher-window   URL 없음   ← 브라우저 확장 미설치
노트북 aw-watcher-afk      URL 없음
폰 aw-watcher-android      URL 없음   ← UsageStats 는 URL 을 모른다
폰 aw-watcher-android-web  소수만 URL 있음
```

그럼 분류는 무엇이 하고 있었나 — **창 제목**이다. 규칙 40개 중 앱만 보는 것이
30개, 제목을 쓰는 것이 4개, URL 만 보는 것이 6개(사문)다. 2번 절 "url 이 없는
브라우저 창을 창 제목으로 세분화"가 실제로 일을 하고 있었다.

폰 web 이벤트도 품질이 낮다. 방문 기록이 아니라 **주소창 텍스트 스냅숏**이다:
`"Google 검색 또는 URL 입력"`(빈 주소창 안내문구), `"국"`, `"인"`(타이핑 중간
글자)까지 url 필드에 들어온다. duration 0~4초.

**다음 수는 노트북 브라우저 확장 설치다.** 5분이면 되고, 그날부터 URL 규칙 6개가
일한다. 폰 web 워처는 접근성 서비스 권한이 필요한데 얻는 데이터 품질이 위와 같아
우선순위가 낮다.

## ★ 밤 — 동기화가 자라는 이벤트의 최종본을 못 잡고 있었다

> 사후 기록: [HISTORY/2026-08-23-sync-kept-the-shortest-version-of-growing-events.md](../../HISTORY/2026-08-23-sync-kept-the-shortest-version-of-growing-events.md)

"폰에 유튜브 틀어놓고 노트북으로 작업했는데 왜 유튜브가 이겼나"에서 시작해
**두 개의 서로 다른 문제**가 나왔다. 하나는 데이터 결함(고침), 하나는 중재 규칙의
한계(미해결).

### 오진 먼저 — "afk 워처가 침묵했다"는 틀렸다

처음엔 노트북 afk 워처가 장시간 보고를 안 했다고 봤다. 우리 DB가 그렇게 보였다:

```
T0~T1 (짧은 구간) not-afk    ← 그리고 긴 공백
```

**AW 서버에 직접 물어보니 침묵한 적이 없었다.** 같은 `timestamp` 로 이벤트가
여러 벌 온다:

```
같은 시작 시각 (긴 최종본) not-afk   ← 진짜 데이터
같은 시작 시각 (짧은 중간본) not-afk ← 우리가 저장한 것
```

AW는 하트비트로 **자라는 중인 이벤트**를 성장 단계별로 다 돌려준다. 같은 timestamp에
여러 duration이 있었고, 여러 그룹이 중복이었다:

```
timestamp A  [짧음, 중간, 최종] → 우리 DB: 짧은 값
timestamp B  [짧음, 중간, 최종] → 우리 DB: 짧은 값
```

`upsert_events` 의 키가 `(bucket_id, ts)` 인데 `ON CONFLICT ... duration=excluded.duration`
이라 **마지막에 온 것이 이겼다.** 순서가 보장되지 않으니 사실상 무작위였고,
실측에서는 짧은 쪽이 자주 남았다.

### 고침 — MAX 로 잠근다

하트비트 이벤트의 duration 은 **자라기만 하고 줄지 않는다.** 그래서 MAX 가
의미상 정확하다.

```sql
ts_end   = MAX(ts_end,   excluded.ts_end),
duration = MAX(duration, excluded.duration),
```

회귀 테스트 2개를 붙였다 — 긴 것 뒤에 짧은 것이 와도, 순서를 뒤집어도 긴 쪽이
남아야 한다(`test_upsert_keeps_the_longer_duration`). 옛 코드에서 실제로 깨지는 것도
확인했다.

### 회수 — 커서를 되돌려 재동기화

재동기화 뒤 저장값이 AW 최종본과 일치했고, 짧은 중간본 때문에 빠졌던 시간이
회복됐다. 날짜별 개인 활동량과 기기별 이동량은 공개본에서 제거했다.

### 남은 문제 — 틀어둔 유튜브가 "마지막 상호작용"으로 잡힌다

고치고 나서도 영상 연속 재생 구간은 여전히 폰이 이긴다. 이건 데이터가 아니라 **중재
규칙 자체**다.

```
노트북 not-afk   T0 시작 ~ T3
폰 영상 세션     T1 시작 ~ T2   ← 연속 재생
```

`_arbitrate_devices` 의 규칙은 "**가장 늦게 시작한 활동 구간이 이긴다**"
(= 마지막 상호작용이 소유한다). 폰 세션이 더 늦게 시작했으니 폰이 가져간다.

진짜 기기 전환에는 맞는 규칙이다. 그런데 **연속 재생은 "만진 것"이
아니라 "틀어둔 것"이고, 규칙이 그 구분을 못 한다.** `known-issues.md` §5 로 옮긴다.


## 밤 — 웹 플래너 세 가지와, 그 과정에서 드러난 것들

사용자가 폰에서 쓰다 보고한 세 가지로 시작했는데, 파 보니 각각 다른 층의 문제였다.

### ① "계획 수정이 반영이 안 됩니다" — 저장은 되고 있었다

DB 를 열어 보니:

```
plan.start_min          12:10   ← 수정이 여기까지는 들어왔다
plan_instance.start_min 12:00   ← 화면이 읽는 건 이쪽
```

`materialize_day` 가 `(plan_id, day)` 기준 **멱등**이라(지운 인스턴스가 되살아나면
안 되므로) **템플릿이 바뀌었을 때 따라갈 경로가 아예 없었다.**
`sync_instances_from_plan()` 을 만들어 PATCH 뒤에 부른다 — 오늘 이후만,
`source='template'` 만, `status` 는 유지.

> **깨진 가정: "계획을 고치면 화면도 바뀐다."** 쓰기 경로와 읽기 경로가 다른
> 테이블을 보고 있었다. 저장 API 부터 판 것이 한 바퀴 낭비였다 —
> **"저장이 안 된다" 는 보고에는 화면이 읽는 테이블부터 본다.**
> [HISTORY](../../HISTORY/2026-08-23-plan-edit-never-reached-the-instance.md)

### ② 시간 입력이 제출을 조용히 막고 있었다

`<input type="time" step="600">` 인데 **안드로이드 네이티브 피커가 `step` 을
무시한다.** 09:13 이 들어가면 `stepMismatch` 가 되고, `required` 와 겹쳐
**브라우저가 submit 이벤트 자체를 안 낸다** — JS 핸들러가 아예 안 불린다.

셀렉트 두 개(시 00~23 · 분 00/10/20/30/40/50)로 바꿨다. **고를 수 없게** 만든
것이라 기기·로케일에 기대지 않는다. 옛 데이터가 09:13 이어도 `snapMinute()` 로
열린다 — 없으면 셀렉트가 첫 항목으로 되돌려 놓아 조용히 시각이 바뀐다.
[HISTORY](../../HISTORY/2026-08-23-input-time-step-is-not-enforced.md)

### ③ 오늘의 기록 → 격자 잇기

기록 목록의 점을 누르면 격자에서 그 구간이 반짝인다. 슬롯 번호는 **서버가 싣는다**
(`slot_start`/`slot_end`) — 시각 문자열에서 클라이언트가 다시 계산하면 06:00 경계
규칙이 두 벌이 된다. 검증: 슬롯 89 ↔ 20:50–21:00.

이웃한 칸이 같은 구간이면 그 변은 긋지 않아 **구간 전체가 한 덩어리**로 보인다.
검은 얇은 선 + 흰 섬광(70%) — 100% 면 그 순간 칸 색(=카테고리)이 가려진다.

### ④ 저장 뒤 화면 교체 — "눈이 약간 아프다"

`location.reload()` 를 여섯 곳에서 그냥 부르고 있었다. `softReload()` 로 묶어
스크롤을 넘기고 190ms 흐려졌다 240ms 에 걸쳐 들어오게 했다.
**흰색으로 날리지 않고 흐려지기만 한다** — 밝게 바꾸면 그것 자체가 또 번쩍임이다.

스크롤 복원은 `history.scrollRestoration = "manual"` 로 브라우저 쪽을 끄고 한 곳에서만
한다 — 둘 다 켜 두면 싸운다.

### 내가 낸 회귀 둘

**마커가 링으로 보였다.** `<span>` 을 `<button>` 으로 바꾸면서
`button.activity-marker { border: none; background: none }` 을 적었는데,
요소+클래스 선택자가 `.activity-marker` 보다 강해서 점의 3px 테두리와 카테고리 색
배경을 지워 버렸다(실측: border 0px, background transparent).
사용자가 "동그라미 짤려있네" 로 잡아 줬다.

**수정 폼을 열면 화면이 요동쳤다.** `scrollIntoView({behavior:"smooth"})` 와
`focus()` 를 폰에서 같이 하면 키보드가 뷰포트를 줄이고 브라우저가 다시 스크롤하는데,
그때 smooth 애니메이션이 아직 돌아 서로를 밀어낸다.

### ★ 실제 브라우저를 붙였다

첫 시도에서 "브라우저 재현을 못 했다" 고 넘어간 것이 실제로 문제였다 —
①의 원인을 못 찾고 ②만 고쳤다가 사용자에게 두 번 보고를 받았다.
`~/.cache/ms-playwright` 에 크로미움이 있었고 `playwright-core` 도 깔려 있어서,
모바일 뷰포트로 각 단계의 상태를 찍을 수 있었다:

```
저장 전 scrollY 900 · 수정폼 연 뒤 1492 · 저장 직전 1492 · 복원 후 1492
PATCH  200  (/d/… 와 /planner/d/… 양쪽)
폼      plan_id=6, 12:00~13:00, "수정 저장"  ← 정상으로 채워짐
```

이게 결정적이었다. API·접두사·폼이 전부 정상이라는 것을 확인했기에
**인스턴스 전개**로 범인을 좁힐 수 있었다. 그리고 "스크롤이 900→1492 로 튄다" 고
본 것도 실은 **내 측정 기준이 틀린 것**이었다(폼을 열면 1492 로 옮겨 간다).
단계별로 찍어 보고서야 갈렸다.

### 임베딩 서버가 새고 있었다

낮에 "3G 로도 부족하다" 고 보고 4G 로 올린 것이 **잘못된 판단**이었다.
부족한 게 아니라 새고 있었고, 여유를 주자 그만큼 더 새서 스왑 7.8GB 를 전부 먹고
8B 까지 끌어내렸다(가용 112MB, 대화가 503).

```
유휴 1.8GB → 요청 약 1,380건 뒤 RSS 1.2GB + 스왑 5.5GB = 6.7GB
재시작하니 즉시 1.8GB   ← 작업량이 아니라 누수다
```

`MemoryMax=2500M` + **`MemorySwapMax=0`**. 새면 스왑으로 기어 들어가 기기 전체를
인질로 잡는 대신 빨리 죽고 빨리 살아난다.
[HISTORY](../../HISTORY/2026-08-23-raising-the-memory-cap-made-it-worse.md)

사용자가 "이건 RAG 냐" 고 여러 번 물어서 실제로 트레이스했다.

| 질문 | 경로 | 툴 |
