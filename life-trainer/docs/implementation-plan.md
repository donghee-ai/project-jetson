## 0. 착수 시점의 실제 상태

설계서는 백지를 가정하지만 이 기기는 백지가 아니다. 먼저 실측했다.

| 항목 | 실제 |
|---|---|
| llama-server | **가동 중**. Qwen3-8B-Q4_K_M, `-c 20480`, `--parallel 1`, RSS **6.7 GB** (08-23 ctx 축소 전 40960 · 10.4GB) |
| OpenClaw 게이트웨이 | 가동 중 (127.0.0.1:18081), Slack Socket Mode 연결됨 |
| Slack 토큰 | `~/.openclaw/openclaw.json` 에 bot/app 토큰 **이미 존재** |
| ActivityWatch | **어디에도 설치돼 있지 않음** ← Phase 1 의 전제인데 비어 있었다 |
| Windows PC `main` | Tailscale 100.64.0.3, **active** |
| Docker | **미설치** |
| 가용 메모리 | 약 4.5 GB (08-23 ctx 축소 전 2.8 GB) |
| GUI | `graphical.target` — 헤드리스 전환 안 됨 (약 0.5 GB 회수 가능) |
| sudo | **비밀번호 필요** — 전력모드·헤드리스 전환은 사람이 직접 해야 한다 |

**가장 큰 발견은 메모리다.** 설계서 §4.3 의 예산표(합계 12.4 GB, 여유 3.5 GB)는
LLM 을 8K 컨텍스트로 잡았을 때의 숫자다. 실제로 도는 서버는 40,960 컨텍스트라
KV 캐시만으로 예산을 다 먹었다. **이 차이가 아래 결정 대부분의 원인이다.**

> **2026-08-23 정정.** 그 40,960 을 20,480 으로 낮췄다 — KV 2.99GB → 1.50GB.
> `-c 40960` 은 `n_ctx_train` 상한이라 고른 값이었지 필요한 값이 아니었다.
> 실측 한 턴 최악이 2,980 토큰이다. 아래 "선결 과제" 항목들은 **이때 해소됐다.**

## 1. 설계서에서 바꾼 것 — 그리고 이유

### 1-1. 별도 모델 서버를 띄우지 않는다

설계서는 Life Trainer 전용 llama.cpp 서버를 상정한다. **불가능하다.**
8B@20480 이 6.7 GB 를 쓰는 지금도 두 번째 8B 서버는 안 들어간다 (당시엔 10.4 GB).
`operate/notes/agent-gateway.md §5` 에 8B 스택과 4B 를 동시에 못 올린 기록이 이미 있다.

→ **기존 `127.0.0.1:8080` 을 공유한다.** `--parallel 1` 이라 llama.cpp 가
요청을 알아서 직렬화하므로, 설계서의 "GPU 단일 큐" 원칙은 서버 수준에서 이미 성립한다.
Life Trainer 의 `job` 큐는 그 위에서 **작업 단위** 직렬화와 재시도를 담당한다.

### 1-2. 임베딩 · 리랭커는 Phase 4 로 미루고, 그 전에 선결 과제가 있다

설계서 §4.2 는 임베딩 0.6B + 리랭커 0.6B (합 2.4 GB) 를 배치 잡 안에서만 로드한다고 했다.
작성 당시 여유가 2.8 GB 라 **이론상 겨우 들어가지만 실제로는 위험**했다.

> **2026-08-23 결과.** ctx 축소로 여유가 4.5 GB 가 됐고, 임베딩(0.6B)은 배치 잡 안이
> 아니라 **상주 서버**(`llama-embed`, CPU, 1.8GB)로 붙었다 — 설계서와 다른 선택이다.
> llama.cpp 는 프로세스당 모델 하나라 대화용 8B 옆에 띄우는 수밖에 없었다.
> **리랭커는 아직 안 붙였다** ([rag-plan §7](rag-plan.md)).

→ ~~**Phase 4 진입 조건**~~ **✅ 2026-08-23 해소.** 컨텍스트를 40,960 → **20,480** 으로
낮춰 KV 1.49GB 를 회수했다. OpenClaw 쪽 `contextWindow` 도 20480 으로 같이 맞췄다
(`operate/notes/agent-gateway.md §4-2`: 한쪽만 바꾸면 조용히 잘린다).

8,192~16,384 가 아니라 20,480 을 고른 이유: OpenClaw 압축 설정
(`maxHistoryShare 0.7` + `reserveTokens 6000`)이 재계산 없이 성립하는 하한이다
(14,336 + 6,000 = 20,336 < 20,480). 더 낮추려면 압축 설정까지 손봐야 한다.

실제로 붙은 것은 임베딩(1.8GB)뿐이고 **리랭커는 아직 안 붙였다** —
[rag-plan §7](rag-plan.md) 대로 4단계 실측 후에도 부족하면 그때 본다.

### 1-3. Docker Compose 를 쓰지 않는다

설계서 Phase 0 에 있으나, 이 기기에 Docker 가 없고 이 저장소의 기존 패턴은
**systemd 사용자 유닛 + venv** 다 (`openclaw-setup/` 참조).
16 GB 공유 메모리에서 컨테이너 런타임은 순수 낭비다.

→ venv + systemd user timer 로 간다. 되돌리기·상태확인 방법이 저장소 안에서 일관된다.

### 1-4. Slack 은 2단계로 간다

| 단계 | 방식 | 얻는 것 |
|---|---|---|
| **지금** | `mode="notify"` — 기존 OpenClaw 봇 토큰 재사용, 발송 전용 | 토큰 발급 없이 **오늘 바로** 리포트 푸시 |
| 다음 | `mode="bolt"` — 전용 앱, Socket Mode | `/lt`, `/log` 슬래시 커맨드 |

전용 앱이 따로 필요한 이유: **같은 앱 토큰으로 소켓 연결을 두 개 열면
이벤트가 어느 쪽으로 갈지 예측할 수 없다** (`measure/findings/slack.md §4`, Slack 문서 직접 인용).
OpenClaw 가 이미 그 앱의 소켓을 쓰고 있으므로 슬래시 커맨드는 별도 앱이어야 한다.
매니페스트는 `config/slack-app-manifest.json` 에 준비해 둔다.

### 1-5. ActivityWatch — Tailscale IP 직접 바인딩은 함정이다

조사 문서(`measure/findings/activitywatch.md §4`)는 Tailscale IP 직바인딩을 1순위로 권한다.
**이 경우엔 틀렸다.** 로컬 워처(`aw-watcher-window`, `aw-watcher-afk`)와 브라우저 확장은
`localhost:5600` 으로 붙는다. Tailscale IP 에만 바인딩하면 **수집이 통째로 멈춘다.**

→ `address = "0.0.0.0"` + **Windows 방화벽을 `100.64.0.0/10`(Tailscale CGNAT)으로 제한.**
평문 HTTP 지만 Tailscale 이 WireGuard 로 감싸므로 그대로 둔다.

### 1-6. api_key 는 데이터가 쌓이는 것을 확인한 뒤에 켠다

aw-server v0.14.0b1+ 는 Bearer 인증을 지원한다. 그런데 **번들된 로컬 워처가
그 키를 실어 보내는지가 버전에 따라 불확실**하다 (PyPI `aw-client` 0.5.15 는 코드 자체가 없다).
켜자마자 수집이 멈추면 원인 추적이 어렵다.

→ 1차: 키 없이 설치 → 데이터 확인. 2차: `-EnableApiKey` 로 켜고 **워처가 계속 기록하는지 재확인.**
스크립트가 이 순서를 강제하고, 실패 시 되돌리는 법까지 출력한다.

### 1-7. 집계의 원천은 `slot` 이 아니라 `slot_breakdown` 이다

설계서 §3.4 의 winner-takes-all 은 **시각화용**이다.
"이번 주 코딩 몇 시간"을 승자 슬롯으로 세면 한 슬롯에서 밀린 시간이 전부 증발한다.

→ `slot` = 144칸 띠를 그리는 용도. `slot_breakdown` = 모든 SQL 집계의 근거.
설계 원칙 2번("집계는 SQL")을 지키려면 이 분리가 필수다.

## 2. 단계 계획

각 단계는 **그 자체로 쓸모가 있어야 한다** (설계서 §9 원칙).

### Phase 0 — 뼈대 ✅

- [x] venv + 의존성 (Python 3.10, `tomli` 추가 — 3.11 미만이라 `tomllib` 이 없다)
- [x] SQLite 스키마 24개 테이블 (WAL, `synchronous=FULL`, FTS5 트리거)
- [x] 설정 계층 (TOML + 환경변수 + **OpenClaw 토큰 자동 폴백**)
- [x] 시간 유틸 (144슬롯 인덱싱, RFC3339 파싱, 기간 문자열)
- **완료 기준**: `load_config()` 가 동작하고 DB 가 생성된다 ✅

### Phase 1 — 활동 로깅 ★ 가장 중요

- ActivityWatch 수집기 (조건부 재조회 + `(bucket, ts)` upsert)
- 합성 데이터 생성기 — **PC 설치를 기다리지 않고 파이프라인 전체를 검증하기 위한 것**
- 규칙 기반 분류기 (40+ 앱, URL·제목 규칙)
- 144슬롯 롤업 (AFK 클리핑 포함)
- 타임라인 PNG (하루 1줄 / 주간 7줄)
- Slack 일일 리포트
- **LLM 없음**
- **완료 기준**: 어제 데이터로 PNG 가 나오고 Slack 에 카드가 게시된다

### Phase 2 — 수집기

- 예의 계층 (도메인별 토큰버킷, 조건부 GET, 적응형 주기, robots.txt)
- RSS / arXiv 수집 + SHA-256 · SimHash 중복 제거
- 키워드 관심사 스코어링 (**LLM 없음**)
- 아침 다이제스트
- **완료 기준**: 재수집 시 대부분이 304 로 끝나고 중복 문서가 안 생긴다

### Phase 3 — LLM 골격

- OpenAI 호환 클라이언트 (**스키마 `pattern` 검증기**, thinking off 강제, 계측)
- `job` 큐 + 리스 + 지수 백오프 + `fcntl` GPU 락
- 핸들러 2종: 미분류 활동 태깅, 문서 요약
- **완료 기준**: 워커가 큐를 비우고 `llm_call` 에 실측 지연이 쌓인다

### Phase 4 이후 — 조건부

RAG(GROBID·임베딩·리랭커)는 **§1-2 의 메모리 선결 과제를 해결한 뒤에** 착수한다.
안 하면 OOM 이다.

## 3. 이 기기의 실측이 강제하는 코딩 규칙

`measure/findings/performance.md` 와 `operate/notes/agent-gateway.md` 에서 나온 것들.
계약서 §0 에 넣어 모든 구현 담당에게 강제했다.

| 규칙 | 근거 |
|---|---|
| **JSON 스키마에 `pattern` 금지** | llama.cpp GBNF 변환기가 정규식을 못 다뤄 요청 전체를 400 으로 거부. 앵커를 붙여도 안 된다 (`operate/notes/agent-gateway.md §4-5`) |
| **JSON 출력 시 thinking 무조건 off** | 사고 텍스트가 섞여 파싱이 깨진다 |
| **LLM 입력 3~5K 로 끊기** | 깊이 3K 10.9 tok/s → 32K 3.96 tok/s (−70%). 30K 1회보다 3K 10회가 2.7배 빠르다 |
| **한국어 토큰 55% 할증** | 같은 내용에 토큰이 1.55배 든다 |
| **파이썬 상주 300 MB 이하** | 여유 4.5 GB (08-23 ctx 축소 전 2.8 GB) |
| **GPU 잡 동시 실행 금지** | `fcntl.flock` 으로 강제. 두 번째 워커는 즉시 종료 |
| **모델 id 까지 확인** | 포트만 보는 헬스체크가 다른 모델을 통과시켜 1시간 무중단 다운을 낸 적 있다 (`operate/notes/agent-gateway.md §4-8`) |

## 6. 구현 중 드러난 것들

계약서만으로는 안 나오고, **실제로 돌려봐야 나온 것들**이다.

### 6-1. `unclassified` 누적이 멱등하지 않았다

롤업은 오늘 것을 10분마다 다시 돌린다. 그런데 미분류 지문의 `seconds_total`/`hits` 를
같은 테이블에 더하는 구조라 재실행마다 부풀어 올랐다. slot/slot_breakdown 처럼
"지우고 다시 쓰기"가 불가능한 형태였던 것.

→ `unclassified_day(day, fingerprint, seconds, hits)` 를 추가해 **날짜별 실적**을 분리했다.
`unclassified` 는 지문의 정체성과 LLM 태깅 결과만 갖고, `seconds_total` 은 그 합계로 **재계산**된다.
태깅 결과(`llm_category` 등)는 재롤업 시 절대 덮어쓰지 않는다.

### 6-2. SimHash 가 SQLite INTEGER 를 넘쳤다

64비트 부호 없는 SimHash 값이 SQLite 의 부호 있는 64비트 `INTEGER` 컬럼에서
입력 절반가량에 `OverflowError` 를 냈다. → 2의 보수 범위로 정규화해 저장하고
`hamming()` 에서 마스킹해 부호 유무와 무관하게 비교되게 했다.

### 6-3. arXiv 는 robots.txt 로 전체를 막아둔다

`export.arxiv.org/robots.txt` 의 실제 내용:

```
User-agent: *
Disallow: /
```

수집기의 robots 처리는 정상 동작했다. **차단이 사실이었다.**
그런데 arXiv API 는 arXiv 가 프로그램 접근용으로 공식 제공하고 별도 이용약관을 둔
전용 인터페이스이고, 설계서 §6 도 "arXiv API 우선, 3초 간격 준수"를 명시한다.

→ 전역으로 robots 를 끄지 않고 **소스 단위 예외**(`sources.yaml` 의 `respect_robots`)를 만들었다.
전역 기본값은 `true` 그대로다. 예외가 적용되면 로그에 남긴다. 되돌리려면 그 한 줄만 지우면 된다.

### 6-4. 합성 데이터가 두 번 틀렸다

1차: 세그먼트를 무작위로 이어 붙이기만 해서 **하루가 13:30 에 끝났다.**
기상~취침 구간과 세그먼트 총합 사이에 아무 관계가 없었던 것. 게다가 현재 시각 이후의
**미래 이벤트**까지 만들고 있었다.
2차: 고쳤더니 이번엔 **10분마다 카테고리가 바뀌는 스트로브**가 됐다.

→ 기상·취침 시각을 먼저 정하고 그 사이를 채우도록 바꾸고, 하루 목표 활동 시간을
먼저 뽑아 세그먼트 밀도를 역산하게 했다. 블록은 길게, 개수는 적게.

단편화의 진짜 원인은 세그먼트 개수가 아니라 **한 세그먼트 안에서 서로 다른 카테고리로
분류되는 앱을 섞은 것**이었다. 예컨대 여가 구간이 `reddit.com`(→browsing)을 뽑거나
회의 구간이 `explorer.exe`(→ops)를 뽑으면, 승자 카테고리가 구간 중간에 뒤집혀
10분짜리 스트로브가 된다. 세그먼트마다 카테고리를 하나로 고정해서 해결했다.

**이건 사소한 문제가 아니다.** ActivityWatch 설치 전까지 합성 데이터가 유일한 검증 수단이자
데모이고, 오후·저녁 슬롯이 통째로 비어 있으면 그 구간의 버그가 드러나지 않는다.

> **미달 항목 (기록해 둔다).** 하루 블록 수(8~11개, 상한 12)와 커버리지·활동 시간은
> 목표에 들어왔으나, **최장 집중 블록이 목표(1~2.5시간)보다 긴 3~6시간**으로 나온다.
> 블록 수 상한과 커버리지 하한을 동시에 만족시키면서 이 값을 줄이지 못했다.
> 합성 데이터의 사실성 문제일 뿐 파이프라인 정확성과는 무관하고,
> 실데이터가 들어오면 자연히 해소된다. 무리해서 맞추면 설정이 취약해지므로 그대로 뒀다.

## 7-B. 플래너 (2차 구현) — 설계서에 없던 것

사용자가 남긴 레퍼런스([refs/reference/planner_example.png](design/refs/planner_example.png))가
**24행 × 6칸 = 144칸, 06:00 시작**이었다. 우리 10분 슬롯과 정확히 같은 격자다.
설계서 §8.2 는 "144칸 가로 띠 하나 = 하루"였는데, 종이 플래너 양식이 더 낫다는 판단으로 바꿨다.

### 왜 PNG 로 끝내지 않았나

플래너는 **채우는 물건**이다. 계획을 넣고 체크하고 틀린 칸을 고쳐야 하는데
Slack 카드는 읽기 전용이다. PNG 만으로는 절반짜리다.

→ **웹 UI(입력) + Slack(알림·기록)** 2층 구조로 갔다.
설계서는 웹 대시보드를 Phase 5 이후로 미뤘지만, 입력이 필요해지면서 앞당겨졌다.

```
젯슨 웹 플래너 ←─ Tailscale HTTPS ─→ 폰·PC 브라우저 (계획 추가·칸 보정)
      │
   SQLite ←─ ActivityWatch 자동 계측 (격자 자동 채움)
      │
   Slack: PNG 스냅샷 + "플래너 열기" 버튼
```

- `slot` = 기계가 계측한 **실제**, `plan` = 사람이 선언한 **의도**. 절대 섞어 저장하지 않는다.
- `slot_override` = 사람이 고친 칸. **롤업이 재생성해도 살아남고**, `slot_breakdown`(실측 원본)은
  건드리지 않는다. 오버라이드는 격자 표시만 바꾸고 집계 숫자는 안 바꾼다.
- 주간 뷰는 **가로 띠를 그대로 유지**했다. 요일 리듬 비교에는 그 형태가 맞다.

### ★ 색을 눈대중으로 고른 게 틀렸다

처음 카테고리 색은 내가 Tailwind 팔레트에서 감으로 골랐다. `dataviz` 스킬의 검증기를
돌려보니 **3개 항목 FAIL**이었다:

```
[FAIL] 채도 하한      #94a3b8 이 회색으로 읽힘 (구조색과 충돌)
[FAIL] CVD 분리       coding↔research ΔE 1.3 (적록색약)
[FAIL] 정상시야 하한   coding↔research ΔE 12.0  ← 색각 정상인 사람도 구분 못 함
```

**coding 과 research 는 이 시스템에서 가장 자주 나오는 두 카테고리다.**
눈으로는 "파랑이랑 보라니까 다르지"였는데 계산해보니 아니었다.

→ 검증된 8슬롯 팔레트로 교체하고 `config/palette.yaml` 을 **단일 원본**으로 만들었다
(웹 CSS 와 matplotlib 이 같은 파일을 읽는다).

교체 후에도 `--pairs all` 은 통과하지 못한다(research↔ops, research↔entertainment).
그래서 **2차 인코딩을 필수 요구사항으로 못 박았다**: 범례 상시 표시,
3칸(30분) 이상 연속 블록에 카테고리 이름 직접 표기, 웹에서는 tap/hover 시 이름 노출.
이걸 빼면 색각 이상 사용자에게 두 카테고리가 같은 색이다.

> **교훈**: 색은 취향의 영역처럼 보이지만 계산 가능한 부분이 있다. 계산 가능하면 계산해야 한다.

### 렌더링해봐야만 나온 결함 3건

1. **계획 테두리가 격자선에 덮여 안 보였다.** 그리기 순서가 (계획 테두리 → 정시 굵은 선)이라
   09:00~12:00 처럼 정시에 맞는 계획은 테두리가 완전히 가려졌다. 계획은 대부분 정시에
   시작하므로 사실상 기능 전체가 죽어 있었다. 픽셀을 직접 찍어보고 발견.
2. **데스크톱에서 격자 행이 110px** 라 하루를 보려면 2600px 를 스크롤해야 했다.
   플래너의 존재 이유가 "하루가 한눈에"인데 그게 깨졌다. 모바일(42px)은 멀쩡했다.
3. **빈 칸에 "빈칸" 라벨이 도배됐다.** 3칸 이상 직접 라벨 규칙을 구조 상태(`off`/`away`)에도
   적용한 탓. 종이 플래너의 빈 칸은 그냥 비어 있다.

셋 다 테스트는 전부 초록불인 상태였다.

### Tailscale 포트 충돌

`openclaw-setup/enable-tailscale-serve.sh` 가 같은 노드에서 이미 `:443` 을 쓰고 있어
플래너는 `:8443` 으로 잡았다. 둘을 같이 켜도 부딪히지 않는다.
