# Life Trainer — 온디바이스 개인 에이전트 설계서

> 대상 하드웨어: Seeed reComputer J4012 (Jetson Orin NX 16GB), 24시간 상시 구동
> 작성 기준일: 2026-08-16

---

## 0. 요약

하루 활동을 10분 단위로 자동 계측하고, 관심사 문서·뉴스를 야간에 수집·요약·색인한 뒤,
Slack을 통해 리포트·알림·질의응답을 제공하는 온디바이스 개인 에이전트.

**설계 3원칙**

1. **수집이 8할이다.** LLM보다 계측 계층이 성패를 가른다.
2. **집계는 SQL, 문장화는 LLM.** LLM에게 숫자를 계산시키지 않는다.
3. **GPU는 단일 자원이다.** GPU를 쓰는 모든 작업은 하나의 큐로 직렬화한다.

---

## 1. 냉정한 진단

### 1.1 진짜 어려운 건 AI가 아니라 데이터 수집

"오늘 하루를 10분 단위로 보여준다"는 요구사항은 LLM 문제가 아니라 계측(instrumentation) 문제다.
데이터 소스를 확보하지 못하면 수동 입력으로 전락하고, 수동 입력 기반 라이프로그는 예외 없이 3일 안에 방치된다.
여기서 먼저 승부를 봐야 한다.

### 1.2 LLM은 집계를 못 한다

"지난주와 비교"를 LLM에게 원시 로그를 던져서 시키면 숫자를 지어낸다.
집계는 반드시 SQL로 계산하고, LLM은 **이미 계산된 숫자를 문장으로 바꾸는 역할만** 해야 한다.
이 원칙을 어기면 시스템 신뢰도가 0이 된다.

### 1.3 알림 피로

개인 에이전트 프로젝트의 사망 원인 1위는 정확도가 아니라 "너무 많이 울려서 뮤트함"이다.
기본값은 다이제스트, 인터럽트는 명시적 룰이 있을 때만.

### 1.4 젯슨 강점 해석 보정

정확히는 "24시간 도니까 느려도 된다"가 아니라
**"지연 허용 작업과 즉시 응답 작업을 분리할 수 있다"**이다.
무거운 파싱·임베딩·요약은 새벽 배치로, 낮에는 GPU를 비워 질의응답용으로 쓴다.

## 2. 시스템 아키텍처

```
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│  활동 수집    │  │   웹 수집     │  │  일정 · 문서  │
│ ActivityWatch│  │RSS·arXiv·GH  │  │캘린더·드라이브 │
└───────┬──────┘  └───────┬──────┘  └───────┬──────┘
        │                 │                 │
        └────────┬────────┴────────┬────────┘
                 ▼                 ▼
      ┌────────────────────────────────────────┐
      │        단일 이벤트 저장소                │
      │  SQLite (WAL) + FTS5 + 벡터 인덱스      │
      └───────────────────┬────────────────────┘
                          ▼
      ┌────────────────────────────────────────┐
      │      GPU 작업 큐 (한 번에 하나)          │
      │  ┌──────────────┐  ┌────────────────┐  │
      │  │  야간 배치    │  │  주간 온디맨드  │  │
      │  │파싱·요약·임베딩│  │검색·리랭크·답변 │  │
      │  └──────────────┘  └────────────────┘  │
      └───────────────────┬────────────────────┘
                          ▼
      ┌──────────────────┐  ┌───────────────────┐
      │    Slack 봇       │  │   웹 대시보드      │
      │리포트·알림·질의    │  │ 10분 단위 타임라인 │
      └──────────────────┘  └───────────────────┘
```

핵심은 **모든 수집기가 하나의 저장소에만 쓰고, GPU를 쓰는 작업은 전부 단일 큐로 직렬화**한다는 점이다.
16GB 공유 메모리에서 LLM과 임베딩 모델이 동시에 올라가려 하면 OOM 아니면 스왑 지옥이 된다.
큐가 하나면 이 문제가 설계 단계에서 사라진다.

## 3. 수집 계층

### 3.1 소스 매핑

| 소스 | 방법 | 얻는 것 |
|---|---|---|
| PC 활동 | ActivityWatch (`aw-watcher-window`, `aw-watcher-afk`) | 앱·창 제목·AFK 여부 — 10분 버킷의 원재료 |
| 브라우저 | `aw-watcher-web` 확장 | URL·탭 제목 |
| 코드 활동 | GitHub API (commits, PR) | "실제로 뭘 만들었나" |
| 일정 | Google Calendar API (read-only) | 계획 vs 실제 대비 |
| 논문·뉴스 | arXiv API, RSS | RAG 코퍼스 |
| 문서 | Google Drive API / rclone | PDF 코퍼스 |
| 수동 보정 | Slack 슬래시 커맨드 | 오프라인 활동 (운동, 이동, 랩 미팅) |

### 3.2 ActivityWatch를 쓰는 이유

- 버킷/이벤트 REST API + 하트비트 API + 쿼리 언어(필터·병합·그룹화) 제공
- `aw-watcher-afk`(키보드·마우스 입력으로 활성/비활성 판정), `aw-watcher-window`(활성 앱·창 제목) 기본 내장
- 이벤트 모델이 `{timestamp, duration, data}` 3필드로 단순
- Python 클라이언트 `aw-client` 존재

직접 만들 이유가 없다.

### 3.3 설계 결정: 수집과 처리 분리

젯슨에 수집기를 두지 않는다.

- ActivityWatch는 **PC에서** 구동
- 젯슨의 `aw-sync` 잡이 10분마다 PC의 `localhost:5600`을 폴링 (Tailscale 경유)
- PC를 껐다 켜도 파이프라인이 깨지지 않음

### 3.4 10분 버킷 정규화 규칙

- 하루 = 144 슬롯
- 각 슬롯은 그 구간에서 **가장 오래 점유한 카테고리 하나**로 결정 (winner-takes-all)
- AFK 구간은 별도 카테고리(`away`)로 분리
- **규칙 기반 분류기(정규식 → 카테고리)를 먼저**, 매칭 실패분만 LLM 태깅
  - 전부 LLM에 넣으면 느리고 일관성도 없다

## 4. 모델 선택

### 4.1 확정: Qwen3-8B

메인 LLM은 **Qwen3-8B**로 확정.

- Orin NX 16GB의 실용 대역은 8B급 Q4~Q6 → 27B/35B급은 애초에 후보 밖
- Q4_K_M 기준 ~5GB로, 임베딩/리랭커와 공존할 메모리 여유가 생긴다
- Apache 2.0, GGUF 배포 성숙, llama.cpp/Ollama 지원 안정적
- Qwen3.5-9B Q4_K_M 한번 고려 해볼것

참고로 이후 Qwen3.5 / 3.6 / 3.8 세대가 나와 있다.
8B급 대체재는 Qwen3.5-9B 정도인데 고려해볼것.
**Phase 3에서 파이프라인이 돌기 시작한 뒤, 동일 프롬프트·동일 평가셋으로 A/B 측정한 다음 판단한다.**
평가셋 없이 모델부터 바꾸면 뭐가 좋아졌는지 알 수 없다.

### 4.2 권장 조합 (2티어 전략)

| 역할 | 모델 | 양자화 | 메모리 |
|---|---|---|---|
| 요약·질의응답 (저빈도·고품질) | **Qwen3-8B** | Q4_K_M | ~5.0 GB |
| 분류·태깅 (고빈도·정형) | Qwen3-1.7B | Q4_K_M | ~1.2 GB |
| 임베딩 | Qwen3-Embedding-0.6B | FP16 / ONNX | ~1.2 GB |
| 리랭킹 | Qwen3-Reranker-0.6B | FP16 | ~1.2 GB |

전부 Qwen3 동일 세대라 토크나이저·프롬프트 포맷이 일관된다. 운영상 이점이 크다.

Qwen3 Embedding 시리즈는 Apache 2.0. 리랭커 성능도 Qwen3-Embedding-0.6B가 뽑은 top-100 후보 위에서 측정된 것이라,
임베딩 + 리랭커 0.6B 페어는 검증된 조합이다. **당초 0.6B 임베딩 선택은 그대로 유지.**

> Qwen3-8B는 thinking 모드를 지원한다. 야간 배치(요약·태깅)에서는 끄고,
> RAG 답변 생성처럼 추론이 필요한 경로에서만 켜는 것을 기본값으로 잡는다.
> 켜두면 토큰 소비가 몇 배로 늘어 배치 시간이 그만큼 길어진다.

### 4.3 메모리 예산 (16GB 공유)

| 항목 | 크기 |
|---|---|
| OS + 서비스 | ~3.0 GB |
| LLM (Qwen3-8B Q4_K_M) | ~5.0 GB |
| KV 캐시 (8K ctx) | ~1.0 GB |
| 임베딩 + 리랭커 | ~2.4 GB |
| DB · 기타 | ~1.0 GB |
| **합계** | **~12.4 GB** |

약 3.5GB 여유. 컨텍스트를 16K로 늘리거나 Q5_K_M으로 올릴 여지가 있으나, 둘 중 하나만 택한다.

운영 수칙:

- GUI 끄기: `sudo systemctl set-default multi-user.target` (~1GB 회수)
- 전력 모드 고정: `sudo nvpmodel -m 0 && sudo jetson_clocks`
- **임베딩/리랭커는 배치 잡 안에서만 로드 후 해제** — 상주 금지
- **스왑으로 모델 올리기 절대 금지.** 로드는 되지만 토큰마다 전체 가중치를 건드려 사용 불가 수준으로 느려진다. 차라리 양자화를 한 단계 낮춘다.
- DB와 로그는 반드시 **NVMe**에. eMMC에 24시간 쓰기 부하 = 수명 급감.

## 5. RAG 설계

### 5.1 파싱

PDF 파싱이 병목이자 품질의 8할.
정확도가 중요하고 24시간 돌릴 수 있으므로, PyMuPDF 텍스트 덤프 대신 **구조 추출**을 쓴다.

- **GROBID** — 논문 특화, TEI XML로 섹션/참고문헌 분리
- **Docling** — 범용 문서 구조 추출

논문 한 편에 1~3분 걸려도 새벽 배치라 무관.

### 5.2 청킹

- 섹션 경계 존중
- 512~1024 토큰, 15% 오버랩
- 청크마다 `{논문 제목, 섹션명}`을 프리픽스로 부착 → 검색 품질 체감 상승

### 5.3 검색 파이프라인

```
질의
 ├─ BM25 (SQLite FTS5) ──┐
 └─ 덴스 (임베딩)  ───────┴─→ RRF 융합 → top-50
                                   ↓
                          리랭커 (0.6B) → top-5
                                   ↓
                              LLM 생성 (인용 포함)
```

리랭킹은 GPU를 놀리지 않고 정확도를 사는 가장 싼 방법이다.

### 5.4 함정 두 개

1. **Qwen3-Embedding은 쿼리에만 instruct 프리픽스를 붙인다.** 문서에는 붙이지 않는다. 양쪽에 다 붙이면 성능이 조용히 떨어진다.
2. **개인 활동 데이터는 RAG로 넣지 않는다.** "지난주 화요일에 뭐 했지"는 벡터 검색이 아니라 SQL 질문이다.

### 5.5 이중 경로 설계

| 경로 | 대상 | 방식 |
|---|---|---|
| 문서 경로 | 논문·뉴스·드라이브 문서 | 하이브리드 RAG |
| 활동 경로 | 개인 활동 로그 | **고정 툴 함수** |

8B 모델에게 자유로운 text-to-SQL을 시키면 틀린다. 대신 함수 시그니처를 주고 인자만 채우게 한다.

```python
get_activity_summary(start: date, end: date, category: str | None)
compare_periods(period_a: DateRange, period_b: DateRange)
get_todos(date: date)
get_study_trend(weeks: int)
```

PAI 프로젝트에서 쓴 Pydantic 스키마 검증 패턴을 그대로 재사용한다.

## 6. 크롤링 예의 (트래픽 제어)

"같은 사이트 10번 방문" 문제 대응:

- **HTML 스크레이핑은 최후수단.** arXiv API, RSS, GitHub API, Hacker News API 우선. arXiv는 요청 간 3초 간격 권장 준수.
- **조건부 GET.** `url_state` 테이블에 ETag / Last-Modified 저장 → 재방문 시 헤더 전송 → 304면 본문 없이 종료. 재방문 대부분이 여기서 공짜가 된다.
- **도메인별 토큰 버킷.** 전역 큐가 아닌 도메인별 rate limiter. 동시 연결 1, 최소 간격 2초.
- **URL 프론티어 테이블.**
  `(url, last_fetched, next_fetch_at, etag, last_modified, content_hash, fail_count)`
  `next_fetch_at`은 적응형 — 3회 연속 무변경이면 주기 ×2, 변경 감지되면 ÷2.
- **중복 제거.** SHA-256으로 완전 중복, SimHash로 근사 중복(뉴스 신디케이션 대응).
- **robots.txt 준수** + 연락처가 포함된 User-Agent. 실패 시 지수 백오프.

## 9. 로드맵

각 단계는 **그 자체로 쓸모가 있어야** 한다. 중간에 멈춰도 손해가 없게.

### Phase 0 — 뼈대 (주말 1회)
- 젯슨 24시간 상시화 (GUI off, `nvpmodel`, NVMe 마운트)
- Docker Compose, SQLite 스키마
- Slack 봇 Socket Mode 에코
- **완료 기준:** Slack에서 `/ping` → `pong`

### Phase 1 — 활동 로깅 (1~2주) ★ 가장 중요
- ActivityWatch 설치, 동기화 잡
- 규칙 기반 카테고리 분류기
- 144슬롯 롤업, 타임라인 PNG
- 매일 23:30 Slack 리포트
- **LLM 없음**
- 이 단계만으로 실사용 가치의 70%가 나온다. 여기서 재미없으면 뒤는 안 만드는 게 맞다.

### Phase 2 — 수집기 (3주차)
- RSS / arXiv 수집기 + 예의 계층 + 중복 제거
- 아침 다이제스트 (아직 키워드 랭킹만)

### Phase 3 — LLM 투입 (4~5주차)
- llama.cpp 서버 + Qwen3-8B Q4_K_M
- GPU 작업 큐
- GBNF / JSON 스키마 강제 출력
- 야간 요약·태깅 배치

### Phase 4 — RAG (6~7주차)
- GROBID 파싱, 청킹, 임베딩
- 하이브리드 검색 + 리랭커
- Slack 질의응답

### Phase 5 — 에이전트화 (8주차)
