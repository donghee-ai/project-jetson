# 프라이빗 모드 — PC(Windows) 계획

> 2026-09-01 · 젯슨 쪽은 이미 들어가 있다. 이 문서는 **본 컴퓨터가 할 일**만 적는다.
> 폰은 [android/docs/private-mode.md](../android/docs/private-mode.md).

> ## ★ 2026-09-04 — 이 헬퍼는 **안 만들기로 했다**
>
> **PC 는 웹 토글로 끝낸다.** 아래 설계는 그대로 두되 **착수하지 말 것** —
> 결정과 되살릴 조건은 [`for_window/01`](../../for_window/01-private-mode-pc-helper.md) 에 있다.
>
> 요지: 폰은 **우리가 만든 앱**이라 안에 넣으면 되지만 노트북은 **순정 ActivityWatch** 다.
> 순정 프로그램을 밖에서 조종하는 스크립트는 업데이트마다 조용히 깨지고,
> **깨진 상태가 곧 프라이버시가 안 걸린 상태**다. 실패 방향이 나쁜 쪽이다.
>
> 젯슨 DB 는 헬퍼 없이도 안 샌다(저장 관문). 받아들인 것은 **PC 로컬 AW DB 에는 남는다** 는 것뿐이고,
> 정리는 `lt private purge --minutes N --aw` 로 한다.

## 왜 PC 는 폰보다 쉽고 또 어려운가

**쉬운 쪽**: PC 의 ActivityWatch 는 **워처가 직접 관측한다.** 폰처럼 OS 로그를 커서로
따라잡는 구조가 아니라, `aw-watcher-window` 가 지금 이 순간의 창을 읽어 aw-server 에
쓴다. **프로세스를 멈추면 뒤에 따라잡을 것이 없다** — 기록 자체가 생기지 않는다.

**어려운 쪽**: 멈춰야 할 것과 살려야 할 것이 갈린다.

| 프로세스 | 프라이빗 중 | 왜 |
|---|---|---|
| `aw-watcher-window` | **멈춘다** | 창 제목이 여기서 나온다 |
| `aw-watcher-afk` | **멈춘다** | "이 시간에 자리에 있었다"도 정보다 |
| `aw-server` | ★ **살려 둔다** | 아래 |
| `aw-qt` (트레이) | 살려 둔다 (단, §죽은 자식 확인) | |

### ★ aw-server 를 멈추면 안 되는 이유가 둘이다

1. **젯슨 `sync()` 가 오류를 쌓는다.** 프라이빗을 켤 때마다 헬스체크가 빨개진다 —
   *안 울려야 할 때 우는 검사*를 새로 만드는 꼴이다 ([CLAUDE.md](../../CLAUDE.md) §1)
2. **aw-client 로컬 큐가 재개 시 밀린 것을 전송한다.** aw-server 만 멈추는 것이
   최악이다 — 워처는 계속 관측하고 큐에 쌓았다가 **한꺼번에 밀어 넣는다.**
   멈춘 것 같은데 안 멈춘 상태다

## 설계 — 상태로 판정한다, 엣지가 아니라

`scripts/lt-private-agent.ps1` — `poll_sec`(기본 15초) 루프.

```
매 주기:
  원하는_상태 = GET /ingest/private   (실패하면 마지막으로 아는 상태 유지)
  실제_상태   = 워처 프로세스가 떠 있나
  둘이 다르면 맞춘다
```

★ **"켜졌다는 통지를 받으면 멈춘다"(엣지)로 만들지 않는다.** 통지 한 번을 놓치면
영원히 어긋나고, 그걸 사람이 알아채는 방법이 없다. 상태 비교는 매 주기 스스로 낫는다.

### 페일세이프 — 헬퍼가 죽었을 때

젯슨에 못 닿아도 `until_ts` 가 **미래면 계속 멈춰 둔다** (조회 실패가 프라이버시를
푸는 방향으로 작동하면 안 된다).

그런데 반대 사고가 있다: **헬퍼가 죽었는데 워처가 멈춘 채면 하루가 통째로 빈다.**
그래서 멈추기 **전에** 파일을 쓴다:

```
%LOCALAPPDATA%\lt-private\resume_at    ← until_ts (epoch 초) 한 줄
```

별도 작업(10분 주기)이 데드맨 스위치를 돈다 — `resume_at` 이 과거인데 워처가 안 떠
있으면 되살린다. **이 작업은 헬퍼와 다른 프로세스여야 한다.** 같은 프로세스가 자기
죽음을 감시할 수는 없다.

### 작업 스케줄러

**"로그온할 때 / 사용자가 로그온한 경우에만"** 으로 등록한다.

★ 서비스로 만들면 **세션 0 격리**로 GUI 프로세스를 못 건드린다. `aw-watcher-window` 는
사용자 세션의 GUI 프로세스라 서비스에서 종료·기동이 안 된다.

## 만들기 전에 PC 에서 재야 하는 것 셋

이 셋을 모르면 스크립트를 확정할 수 없다. **추측으로 쓰면 조용히 안 멈춘다.**

| # | 확인할 것 | 어떻게 | 왜 갈리나 |
|---|---|---|---|
| 1 | 워처 exe **경로와 기동 인자** | `Get-CimInstance Win32_Process -Filter "name like 'aw-watcher%'" \| Select Name, ProcessId, CommandLine` | 다시 켤 때 같은 인자로 켜야 한다. `--testing` 같은 게 붙어 있으면 빼먹으면 다른 버킷에 쓴다 |
| 2 | **`aw-qt` 가 죽은 자식을 되살리나** | 워처 하나를 죽이고 60초 관찰 | 되살린다면 워처만 죽여선 안 멈춘다 — aw-qt 설정에서 그 워처를 빼거나 aw-qt 도 같이 다뤄야 한다 |
| 3 | 워처 종료 시 **로컬 큐가 재개 후 flush 되나** | 워처 정지 → 3분 → 재개 → 젯슨에서 그 3분 조회 | flush 된다면 "멈춤"이 아니라 "지연"이다. 그러면 §소급 삭제에 의존해야 한다 |

★ 3번이 이 설계의 전제다. **flush 되면 PC 도 폰과 같은 부류가 된다** —
멈추는 것만으로 부족하고 재개 뒤 정리가 반드시 필요해진다.

```powershell
# 1번 — 그대로 붙여 넣어 실행하고 출력을 아래 표에 적는다
Get-CimInstance Win32_Process -Filter "name like 'aw%'" |
  Select-Object Name, ProcessId, CommandLine | Format-List
```

| 확인 | 결과 |
|---|---|
| 1 워처 경로·인자 | ⬜ 미측정 |
| 2 aw-qt 부활 | ⬜ 미측정 |
| 3 큐 flush | ⬜ 미측정 |

## 그때까지 PC 는 어떻게 되나 — **이미 막혀 있다**

★ 헬퍼가 없어도 **젯슨 DB 에는 안 들어간다.** 저장 관문(`upsert_events`)이 프라이빗
구간과 겹치는 부분을 잘라내기 때문이다. 웹 토글은 지금도 완전히 동작한다.

헬퍼가 더하는 것은 **PC 로컬 AW DB 에도 안 남게** 하는 것이다. 그 전까지는
`lt private purge --minutes N --aw` 로 사후 정리할 수 있다
(`cfg.private.purge_aw = true` 면 자동).

| | 지금 (헬퍼 없음) | 헬퍼 도입 후 |
|---|---|---|
| 젯슨 DB | ✅ 안 들어간다 | ✅ 안 들어간다 |
| PC 로컬 AW DB | ⚠️ 남는다 (`--aw` 로 사후 삭제) | ✅ 애초에 안 생긴다 |
| 커버리지 표시 | ✅ 프라이빗으로 구분 | ✅ 〃 |

**이 순서가 맞다.** 관문이 먼저고 헬퍼는 그 위의 층이다 —
반대로 만들었으면 헬퍼가 죽는 순간 전부 새어 들어왔다.
