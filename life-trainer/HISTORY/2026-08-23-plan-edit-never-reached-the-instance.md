# 계획을 고쳐도 화면이 안 바뀌었다 — 템플릿만 고치고 인스턴스는 그대로였다

- **발견**: 사용자가 "예시 일정 시간을 바꾸려는데 안 되네요" 라고
  두 번 보고. 첫 보고 때 API·경로·폼을 다 뒤졌고 전부 정상이었다. DB 를 직접 열어
  보고서야 갈렸다.

- **증상**: 계획 수정 폼에서 시간을 바꾸고 저장하면 성공처럼 보이는데(오류도 없고
  페이지도 새로 그려진다) 화면의 시간이 그대로다. 다시 열어 보면 폼에는 바꾼 값이
  들어 있다 — 저장은 됐는데 안 보인다.

- **원인**: **"계획을 고치면 화면도 바뀐다"** 를 사실이라고 믿었다.

  ```
  plan.start_min          변경값   ← 수정이 여기까지는 들어왔다
  plan_instance.start_min 이전값   ← 화면이 읽는 건 이쪽
  ```

  `materialize_day()` 는 `(plan_id, day)` 기준으로 **멱등**이다 — 한 번 만들어진
  인스턴스는 다시 만들지 않는다. 그건 의도된 설계다(사용자가 지운 인스턴스가
  10분마다 도는 롤업에 의해 되살아나면 안 된다). 문제는 그 멱등성 때문에
  **템플릿이 바뀌었을 때 따라갈 경로가 아예 없었다**는 것이다.

  화면·리포트·플래너 PNG 가 전부 `plan_instance` 를 읽으므로, 사용자 입장에서
  `plan` 은 존재하지 않는 테이블이나 마찬가지였다.

- **수정**: `plan.models.sync_instances_from_plan()` 을 만들어 PATCH 뒤에 부른다.
  - `from_day`(오늘) 이후만 — 과거는 기록이다. `delete_plan` 과 같은 원칙으로
    "앞으로 이렇게 한다" 이지 "그때도 그랬다" 가 아니다. 소급하면 주간 통계가 바뀐다
  - `source='template'` 만 — 손으로 만든/옮긴 인스턴스를 덮으면 그 편집이 사라진다
  - `status`·`note`·`ordinal` 은 안 건드린다 — 시간을 옮겼다고 완료가 풀리면 안 된다

- **방어**: `tests/test_plan.py` 에 6건 — 오늘 이후만 따라간다 / 과거는 그대로 /
  `manual` 은 안 덮는다 / `done` 이 유지된다 / 제목·카테고리도 따라간다 / 없는 계획이면 0.

- **교훈**: **쓰기 경로와 읽기 경로가 다른 테이블을 볼 때를 의심한다.**
  이 저장소에는 그런 쌍이 더 있다 — `plan`↔`plan_instance`, `slot`↔`slot_breakdown`,
  `doc`↔`doc_fts`/`doc_embedding`. 뒤의 둘은 트리거와 `source_hash` 로 이미 이어 놨는데
  계획만 빠져 있었다. **"저장이 안 된다" 는 보고를 받으면 저장 API 부터 보지 말고
  화면이 읽는 테이블부터 본다.** 이번에 API 를 먼저 판 것이 한 바퀴 낭비였다.
