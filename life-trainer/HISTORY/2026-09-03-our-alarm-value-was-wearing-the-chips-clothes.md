# 우리가 정한 92°C 가 칩의 한계 행세를 하고 있었다

> 2026-09-03 · `measure/tools/thermal-test.sh` · 옛 `issues/0020` (고쳐서 여기로 옮겼다)

## 깨진 가정

**"숫자를 적어 두면 다음 사람이 그 출처를 안다."**

모른다. 숫자만 남으면 **하드웨어 사실로 읽는다.**

## 무엇이 틀려 있었나

```
:5    "40W 모드에서 tj 온도가 어디까지 오르는지"     ← 이 보드에 40W 모드가 없다
:74   "⚠️ tj 92C 초과 — 스로틀링 영역"              ← 92°C 는 우리가 정한 값이다
```

이 보드(Orin NX 16GB)의 모드는 `nvpmodel.conf` 가 말하는 대로 **MAXN · 25W · 15W · 10W** 다.
40W 는 Orin AGX 것을 옮겨 적은 것으로 보인다.

그리고 *"스로틀링 영역"* 이라고 단정하면 읽는 사람은 92°C 를 BSP 임계값으로 읽는다.
그러면 **"아직 88°C 니 칩 기준으로 여유가 있다"** 같은 판단이 나오는데,
그 판단의 근거가 실은 우리 자신이다.

## 미확인이 아니었다 — 커널이 답한다

이슈에 *"이 모듈의 실제 throttle threshold 를 확인 못 했다"* 고 적혀 있었다.
문서를 찾을 필요가 없었다. **커널 sysfs 가 갖고 있다:**

```
cpu/gpu/soc-thermal   passive  99°C   critical 104°C
tj-thermal            active   35 / 74 / 95°C · critical 104°C
```

우리 92°C 는 BSP 스로틀 99°C **아래**였다 — 보수적인 값이었고, 그 자체는 옳았다.
틀린 것은 값이 아니라 **그것을 칩의 말인 것처럼 적은 것**이다.

## 무엇을 바꿨나

- 머리말의 "40W 모드" → 이 보드의 실제 모드
- 경보 상수에 이름과 출처를 붙였다 — `WARN_TJ=92 # 프로젝트 판단`
- **BSP 값을 실행 시점에 커널에서 읽는다.** 하드코딩하면 BSP 판올림 때 또 어긋난다
- 헤더와 판정에서 **둘을 나란히** 찍는다:

```
  경보값   : 92C (이 프로젝트가 정함 · 칩 한계 아님)
  BSP     : 스로틀 99C · critical 104C (커널 sysfs)
  ...
  ✅ 온도 여유 충분 (경보값 92C · BSP 스로틀 99C)
```

경보값을 넘으면 **BSP 까지 얼마나 남았는지도 같이** 말한다 — 넘은 선이 누구 것인지
알아야 판단이 선다.

## 곁다리 — 돌려보고 나서야 보인 것

고친 김에 10초만 돌려봤더니 **GPU% 칸이 깨져 있었다:**

```
5s   63.406C 3
98%  918MHz ...
```

`grep -oE "GR3D_FREQ [0-9]+%" | grep -oE "[0-9]+"` 가 **"GR3D" 의 3 을 같이 집는다.**
`tj@` 와 `VDD_IN` 은 앞부분에 숫자가 없어 무사했고, 그래서 이 한 칸만 오래 깨져 있었다.

> **[HANDOFF §8](../HANDOFF.md) 4번** — *"테스트가 통과하는 것과 동작하는 것은 다르다.
> 산출물을 실제로 열어봐라."* 이 스크립트에는 테스트가 없었고, 그래서 아무도 안 열어봤다.
