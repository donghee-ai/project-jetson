# ActivityWatch 이벤트 겹침으로 자리비움이 물리적 범위를 넘었다

- **발견**: 실기기(노트북 `DESKTOP-EXAMPLE`)를 처음 연결하고 **첫 롤업 5분 만에.**
  테스트 584개는 전부 초록불이었다.
- **증상**: 첫 실데이터 요약에서 관측 구간보다 자리비움 합계가 더 길었다.

  개인별 활동·자리비움·관측 시각은 공개본에서 제거했다. 물리적으로 불가능한 값이었다.

## 원인

두 겹이었다.

**상류(ActivityWatch) 쪽** — 서버가 잠깐 죽어 있는 동안 워처는 이벤트를
`aw-client\queued\*.persistqueue` 에 쌓는다. 서버가 살아나면 **자라던 하트비트 하나가
성장 단계마다 개별 이벤트로** 한꺼번에 들어온다. 사본에서 시작 시각이 아주 조금씩
다르고 duration 만 자라는 중복을 확인했다. 서버 API도 같은 시각에 id가 다른 행을
그대로 준다. 개인별 시각·길이·id는 공개본에서 제거했다.

**우리 쪽 — 이게 진짜 문제다.** 롤업이 이벤트별 겹친 초를 **단순 합산**하고 있었다.
겹치는 행을 다 더하니 실제 구간보다 몇 배 긴 값이 됐다.

### 깨진 가정

`docs/research/activitywatch.md §3` 에 이렇게 적어뒀었다:

> 이벤트는 **겹치지 않는다** (하트비트 병합 로직이 음수 duration 을 거부한다)

**이 조사는 `aw-server-rust` 소스를 읽고 쓴 것이다.** 실제로 붙인 노트북은
**파이썬 `aw-server` v0.13.2** 였다. 구현이 다르면 보장도 다르다.
게다가 큐 재생이라는, 어느 구현에서도 문서화되지 않은 경로였다.

## 수정

`lifetrainer/rollup/rollup.py` 에 `_dedupe_overlaps()` 추가.
`_fetch_day_events()` 가 **버킷별로** 이벤트를 겹치지 않는 타임라인으로 정규화한 뒤
넘긴다. 규칙은 하나다 — **뒤 이벤트가 앞 이벤트를 자른다.**

버킷은 본질적으로 하나의 타임라인이고, 같은 순간에 두 상태가 동시에 참일 수 없다.
나중 관측을 신뢰한다. 완전히 덮인 이벤트는 길이 0 이 되어 사라진다.

수정 뒤 자리비움 합계가 실제 관측 범위 안으로 돌아왔다.

> 버킷 **타입별**이 아니라 **버킷 ID 별**로 정규화한다. 기기가 둘 이상이면
> 서로 다른 기기의 이벤트를 잘라내면 안 된다.

## 방어

`tests/test_rollup_overlap.py` (6건):

- 실제로 본 형태(시작이 거의 같고 duration 만 자라는 중복)가 실제 경과 시간 이내로 접히는지
- **정상 데이터는 손대지 않는지** ← 이게 깨지면 기존 집계가 전부 틀어진다
- 부분 겹침에서 뒤 이벤트가 이기는지, 겹친 구간이 두 번 세어지지 않는지
- 완전히 덮인 이벤트가 사라지는지
- **롤업 전 구간을 통과시켜 슬롯 불변식(`active+afk+gap==600`)이 유지되는지**

마지막 것이 최종 방어선이다. 상류가 어떻게 이상해지든 활동 시간이 물리적으로
불가능한 값을 넘길 수 없다.

## 교훈

**합성 데이터로는 절대 못 잡았을 버그다.** 우리 생성기는 정의상 겹치지 않는 이벤트만
만든다 — 그렇게 만들라고 계약서에 써뒀다. 자기가 만든 가정 위에서 자기를 검증한 셈이다.

세 가지를 기억할 것:

1. **조사 문서는 "그 구현"에 대한 사실이지 "그 제품"에 대한 사실이 아니다.**
   붙일 대상의 실물(버전·구현체)을 먼저 확인하라. 우리는 Rust 서버를 조사하고
   파이썬 서버에 붙였다.
2. **외부 데이터의 형식 보장을 신뢰하지 말고 코드로 강제하라.** 정규화는 싸고,
   상류가 이상해지는 경우는 반드시 온다 (여기서는 서버 재시작이라는 흔한 사건이었다).
3. **합성 데이터의 가치는 파이프라인 검증까지다.** 데이터 품질 문제는 실물에서만 나온다.
   실기기 연결을 "마지막 단계"로 미루면 이런 게 마지막에 몰린다.
