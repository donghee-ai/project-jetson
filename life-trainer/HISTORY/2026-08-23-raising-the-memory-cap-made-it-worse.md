# 임베딩 서버 상한을 올렸더니 스왑을 다 먹고 8B 까지 끌어내렸다

- **발견**: 초록 백필 뒤 780건을 재임베딩하는 도중 임베딩 서버가 연결을 끊었다.
  "3G 로도 모자라다" 고 보고 4G 로 올렸다. 그 뒤 대화가 503 을 뱉기 시작해
  `free` 를 봤더니 스왑이 100% 였다.

- **증상**: `llama-server`(8B)가 죽고 재시작. Slack 대화가
  "지금 LLM 서버에 연결할 수 없습니다" 를 반환. 기기 전체가 느려짐.

  ```
  llama-embed   RSS 1,185MB + 스왑 5,526MB = 6.7GB   ← 610MB 모델이
  스왑          7,821 / 7,821MB (100%)
  가용            112MB
  ```

- **원인**: **"죽는 건 상한이 모자라서다"** 를 사실이라고 믿었다.
  모자란 게 아니라 **새고 있었다.** 유휴 상주는 1.8GB 인데 요청 약 1,380건
  (백필 600 + 재임베딩 780)을 처리하고 나니 6.7GB 였다. 재시작하니 즉시
  1.8GB 로 돌아왔다 — 작업량이 아니라 누수다.

  더 나쁜 것은 **여유를 준 것이 해로웠다**는 점이다:

  ```
  2G → 스왑으로 2.4GB 밀림 (느려짐)
  3G → OOM 으로 죽고 재시작        ← 자가복구된다. 이게 제일 나았다
  4G → 스왑 7.8GB 를 전부 먹고 8B 까지 끌어내렸다
  ```

  cgroup 상한은 "여기까지만 쓰라" 가 아니라 **"여기를 넘으면 스왑으로 밀어낸다"**
  이다. 스왑을 허용한 채 상한만 올리면, 새는 프로세스에게 기기 전체를 끌어내릴
  자유를 더 주는 것이 된다.

- **수정**: `MemoryMax=2500M` 으로 낮추고 **`MemorySwapMax=0`**.
  새면 스왑으로 기어 들어가는 대신 빨리 죽고 `Restart=on-failure` 로 빨리 살아난다.
  배치는 `flush_every` 단위로 커밋하므로 중간에 죽어도 재실행이 이어 한다.
  근본 원인(llama.cpp 임베딩 서버 누수)은 안 고쳤다 —
  큰 배치 뒤에는 `systemctl --user restart llama-embed` 가 안전하다.

- **방어**: 유닛 파일에 세 값의 실측 결과를 표로 남겼다. 테스트는 없다(운영 설정).

- **교훈**: **"상한에 걸려 죽는다" 는 상한이 작다는 뜻이 아니다.**
  먼저 "재시작하면 돌아오는가" 를 본다 — 돌아오면 누수고, 상한을 올리는 것은
  증상을 키우는 처방이다. 그리고 **메모리 상한과 스왑 허용은 세트로 정한다.**
  스왑이 열려 있으면 상한은 "죽는 선" 이 아니라 "느려지기 시작하는 선" 일 뿐이고,
  그 뒤로 기기 전체가 인질이 된다.
