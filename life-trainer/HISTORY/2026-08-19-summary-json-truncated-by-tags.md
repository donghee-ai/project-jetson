# 야간 요약을 처음 돌리자마자 JSON 이 문자열 중간에서 잘렸다

- **발견**: 야간 배치를 큐에 넣고 **처음 실제로 돌린 5분 만에.** 워커 로그를 보다가.
  이 핸들러는 08-16 에 만들어져 테스트도 통과한 채로 3일간 한 번도 실행되지 않았다.
- **증상**: `LLM JSON 응답 파싱 실패 (purpose='summarize_doc'): Unterminated string`.
  잡이 3번 재시도하고 실패한다 — **요약 하나에 GPU 1분 이상을 쓰고 아무것도 안 남는다.**

## 원인 — 무엇을 사실이라고 잘못 믿었나

`max_tokens=400` 은 "3~4문장 요약"에 넉넉한 값이라고 믿었다. 요약은 실제로 넉넉했다.
**태그가 넉넉하지 않았다.**

```
'{\n  "summary": "Jetson Orin Nano에서 llama.cpp VLM 컨테이너가 …요청.",\n
  "tags": ["Jetson Orin Nano", "NvMap allocator", "CUDA runtime", "llama.cpp",
  "JetPack 7.2", "SBSA-linux", "Tegra", "OOM-kill", "KV-cache",
  "NVIDIA 컨테이너 도구", "모델 서버", "메모리 누수", "GPU 메모리 관리",
  "LLM", "VLM", "Gemma 3 4B", "docker",          ← 여기서 끊김
```

스키마의 `tags: list[str]` 에 **상한이 없었다.** 8B 는 기술 문서를 받으면 태그를
16개까지 뽑는다. 한국어 토큰이 55% 비싸다는 것까지 겹쳐 요약 + 태그가 400토큰을
넘겼고, GBNF 는 **문법적으로 유효한 접두사**를 만들다가 상한에 걸려 잘렸다.

**JSON 스키마 강제는 "잘린 JSON"을 막아주지 않는다.** 문법을 강제할 뿐 길이를 모른다.

## 수정

프롬프트로 부탁하는 대신 **스키마로 막았다.**

```python
tags: list[str] = Field(description="핵심 키워드 태그 (최대 6개)", max_length=6)
#                       -> JSON Schema 의 maxItems: 6, llama.cpp GBNF 가 강제한다
```

- `maxItems` 는 `pattern` 과 달리 GBNF 변환기가 처리한다 — 실기기에서 400 없이 통과 확인.
- 프롬프트("6개 이하로")도 같이 고쳤다. 스키마와 프롬프트가 다른 말을 하면 안 된다.
- 검증: 같은 문서로 재호출 → 태그 정확히 6개, JSON 완결, 파싱 성공.

**Field description 은 그대로 프롬프트에 실린다.** 처음엔 이 근거를 클래스
docstring 에 적었는데, pydantic 이 그걸 `description` 으로 넣어 매 호출 입력이
150토큰 늘어난다는 걸 보고 주석으로 옮겼다.

## 방어

없음 — 정확히는 **테스트로 못 잡는다.** 이 실패는 "모델이 얼마나 길게 쓰는가"에
달려 있어 목 응답으로는 재현되지 않는다. 대신 구조로 막았다:
스키마에 상한이 있으면 모델이 아무리 길게 쓰려 해도 문법이 허용하지 않는다.

같은 부류를 막으려면 **`max_tokens` 가 있는 모든 JSON 핸들러의 배열 필드에 상한이
있는지** 보면 된다. 지금 있는 것은 `DocSummary.tags`(상한 6)와
`_BATCH_TAG_SCHEMA.tags`(입력 개수만큼만 나오므로 사실상 상한 있음) 둘뿐이다.

`lt doctor` 9항목 OK 였고, 큐에 넣는 곳이 없어서 한 번도 실행되지 않았다.
넣자마자 5분 만에 터졌다.

**실행 자체가 없었으므로 동작 여부는 애초에 미지수였다.**
