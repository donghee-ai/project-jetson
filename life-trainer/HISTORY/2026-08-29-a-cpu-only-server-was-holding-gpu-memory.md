# CPU 전용이라고 적어 둔 서버가 GPU 메모리 646MB 를 쥐고 있었다

- **발견**: 스왑을 조사하다 `/proc/<pid>/status` 의 `VmRSS` 와 `smaps_rollup` 의 `Rss` 가
  안 맞는 것을 보고 파고들었다. 8B 는 6,724 vs 502MB, 임베딩은 2,171 vs 1,649MB 였다.
  `smaps` 는 nvmap/dmabuf 매핑을 못 세므로 **그 차이가 곧 GPU 쪽 메모리**다.

  ```
                     VmRSS    smaps    차이 = GPU(nvmap)
  Qwen3-8B          6,724MB    502MB       6,222MB   ← 가중치 4.68G + KV 1.50G. 맞다
  Qwen3-Embedding   2,171MB  1,649MB         522MB   ← -ngl 0 인데 왜 있나
  ```

- **증상**: 유휴 상주가 1.8GB. 610MB 모델치고 크다는 것은 알고 있었지만
  ([08-23](2026-08-23-raising-the-memory-cap-made-it-worse.md)) 원인을 계산 버퍼로 봤다.
  실제 내역은 이랬다 (신규 기동 직후 실측):

  ```
  dmabuf(nvmap)   646MB   ← CPU 전용 서버가 쥐고 있던 GPU 메모리
  CUDA 코드 매핑   582MB   ← libcublasLt 242 · libggml-cuda 183 · libcublas 119
  익명            593MB   ← 모델 610MB 가 여기 들어 있다 (GGUF 를 mmap 하지 않는다)
  ```

  **모델은 소수파였다.** 그리고 cgroup 기준으로는 더 나쁘다 — `MemoryCurrent` 가
  기동 직후 1,927MB 로, `MemoryMax=2500M` 아래 여유가 573MB 뿐이었다.

- **원인**: **`-ngl 0` 이면 GPU 를 안 쓴다**를 사실이라고 믿었다.
  `-ngl 0` 은 *레이어를 GPU 에 올리지 않는다*는 뜻이지 *CUDA 백엔드를 켜지 않는다*는
  뜻이 아니다. llama.cpp 는 CUDA 빌드로 만들어졌으면 장치가 보이는 한 백엔드를
  초기화하고 컨텍스트·버퍼를 잡는다. 유닛 주석은 *"GPU 에 올렸더니(-ngl 99) 3,144MB 로
  불어 8B 가 기동에 실패했다"* 고 적고 **안 올리는 쪽을 선택했는데**, 안 올려도
  절반은 그대로 붙어 있었다.

  같은 부류를 이 저장소는 이미 안다 — *살아 있다 ≠ 서빙 가능하다*, *툴을 불렀다 ≠ 일을 했다*.
  여기서는 **끄는 플래그를 줬다 ≠ 꺼졌다** 였다.

- **수정**: 유닛에 `Environment=CUDA_VISIBLE_DEVICES=` 를 추가했다. 장치가 안 보이면
  백엔드가 초기화를 건너뛴다. 아레나 쪽으로 `MALLOC_ARENA_MAX=2` 와
  `MALLOC_TRIM_THRESHOLD_=131072` 를 같이 넣었다.

  ```
                    dmabuf   VmRSS(기동)   cgroup(기동)   여유
  전               646MB       1,793MB       1,927MB     573MB
  후                 0MB       1,702MB       1,323MB   1,177MB
  ```

  **cgroup 헤드룸이 2배가 됐다.** 대조 실험(같은 실문서 40건 × 2회):

  ```
  대조군   8번째 요청(32건)에서 OOM 사망
  실험군   80건 생존. 2,862MB 에서 평탄
  ```

- **방어**: 유닛 파일에 실측 내역과 되돌리는 법을 적었다. 자동 검사는 없다 —
  운영 설정이고, 이 기기에서만 재현되는 값이다. 다만 `operate/tools/host-status.sh` 가
  이미 기기 지표를 보고 있으므로 붙일 자리는 있다.

- **교훈**: **`VmRSS` 하나로 판정하지 않는다.** `smaps_rollup` 과의 차이가
  통합 메모리 기기에서 GPU 할당을 드러낸다 — `ps` 만 보면 이 646MB 는 안 보이고,
  "610MB 모델이 왜 1.8GB 인가" 가 영영 안 풀린다.

  **그리고 RSS 합으로 회수량을 예측하지 않는다.** 공유 페이지를 프로세스마다 세므로
  항상 과대추정된다. 같은 날 세 번 나왔다:

  ```
  8B          VmRSS 6,724 vs smaps 502     ← nvmap 을 smaps 가 못 센다
  임베딩       VmRSS −91  vs cgroup −604    ← CUDA .so 582MB 를 8B 와 공유
  gdm 세션     RSS 합 362 vs 실측 회수 165  ← GUI 라이브러리를 37개 프로세스가 공유
  ```

  **예측에는 `Pss`(공유분을 나눠 갖는 값)를 쓴다.** `smaps_rollup` 이 준다 —
  임베딩은 `Rss 1,649` 에 `Pss 1,319` 였다.

  그리고 **끄는 플래그는 무엇을 끄는지 확인한다.** `-ngl 0` 처럼 이름이 결과를
  약속하는 플래그일수록 그렇다. 확인 방법은 프로세스의 실물이다 —
  `grep dmabuf /proc/<pid>/maps` 한 줄이면 됐다.

  > **08-23 의 "누수" 판정도 같이 재봤다.** 같은 요청을 반복하면 자라다가 **평탄해진다**
  > (짧은 문장 60건 +81MB · 1,600자 문서 80건 +1,178MB, 둘 다 이후 증가 없음).
  > 증가분을 정하는 것은 요청 수가 아니라 **입력 길이**다. 무한 누수가 아니라
  > 입력 길이에 비례한 버퍼를 잡고 안 돌려주는 것이다 —
