# 상류의 시계가 **뒤로 흘러서** 이벤트 하나가 여럿이 됐다

- **날짜**: 2026-09-07 (발견 2026-09-03, `docs/issues/0027` 두 번째 기제)
- **깨진 가정**: **"중복은 `event_id` 로 갈린다."**
  상류가 **새 id 를 붙여** 발행하면 그 방법이 안 통한다.

## 남아 있던 절반

`0027` 의 첫 기제는 이미 고쳐져 있었다 — aw-server 가 **질의 창에 맞춰 잘라서** 주고,
잘린 `ts` 가 PK `(bucket_id, ts)` 에 새 키로 들어가 행이 하나 더 생기는 것.
`_absorb_clipped_view` 가 **같은 `event_id` + 겹침**으로 그걸 흡수한다.

그런데 PC afk 버킷은 그 뒤에도 총합이 합집합보다 크게 부풀어 있었다. 다른 기제였다.

## 원인 — 서로 다른 두 시계

`aw_watcher_afk/afk.py` 는 매 폴링(5초)마다 이렇게 만든다:

```python
last_input = now - timedelta(seconds=seconds_since_input)
self.ping(afk, timestamp=last_input + td1ms, duration=seconds_since_input)
```

`now`(시스템 시계)와 `seconds_since_input`(OS 유휴 타이머)은 **다른 시계**다.
자리를 비운 동안 `last_input` 은 고정돼야 하는데, 두 시계가 어긋나면 재계산할 때마다
조금씩 달라진다. 그리고 서버의 병합 조건은:

```python
last_event.timestamp <= heartbeat.timestamp <= pulseperiod_end
```

**하트비트가 저장된 것보다 조금이라도 이르면 병합하지 않는다.** 새 행이 된다.

익명화한 사본 표본에서 `id` 가 오를 때 `ts` 가 계속 내려갔다. 우연한 흔들림이 아니라
**단조 하강**이다. 개인별 시각·행 수·드리프트 길이는 공개본에서 제거했다.

키를 누르면 `last_input` 이 **진짜로** 앞으로 가서 드리프트를 압도한다.
그래서 **몇 시간 동안 입력이 없을 때만** 드러난다.

## 수정 — 임계값 대신 뜻으로 판정한다

이슈는 *"시작이 몇 ms 안이면 같은 것"* 을 제안하고 있었다. 그 숫자에 근거가 없다.
대신 이렇게 판정한다:

> **같은 버킷 · 같은 내용(app·title·url·status) · 구간이 겹친다 → 같은 사건**

창 워처의 타임라인은 한 번에 하나만 포커스다 — *같은 창이 겹친 두 구간* 은 성립하지 않는다.
afk 도 같은 상태가 겹쳐 두 번 있을 수 없다. 조건이 참이면 실제로 같은 사건이고,
**고를 숫자가 없다.**

두 가지를 일부러 **안** 합친다:

- **맞닿기만 하는 것**(끝 == 다음 시작). 같은 앱을 연달아 쓴 것은 진짜로 두 구간이다
- **0초 시점 사건**. `aw-watcher-android-unlock` 은 전부 0초라 **개수 자체가 뜻이다** —
  합치면 세는 것을 줄이는 쪽으로 조용히 틀린다

## 재기 전에는 안 넣었다

개발 사본(`lt dev-db`)의 모든 버킷에 규칙을 적용해 행 수는 줄되 덮은 시간은 유지되는지
검증했다. 개인별 버킷 행 수와 누적 시간은 공개본에서 제거했다.

**불변식은 "행이 준다" 가 아니라 "덮은 시간이 안 변한다" 다.** 일곱 버킷 모두
허용 오차 안에서 같았다. 그리고 영향받지 않아야 할 버킷이 그대로라는 것이, 이 규칙이 무딘 칼이
아니라는 증거다.

그다음 사본을 롤업해서 **사람이 보는 숫자**를 여러 날 비교했다 — 활동 시간·수면 시간
모두 운영과 동일했다. *내가 잰 것과 사람이 겪는 것은 다르다* 를 여기서 닫았다.

## ★ 폰 버킷은 **다른 사건**이었다 — 앱을 안 고쳐도 된다

`aw-watcher-android` 도 중복 쌍이 있었다. 같은 원인이라고 넘어갈 뻔했는데,
모양을 보니 전혀 달랐다:

```
PC afk (드리프트)      시작만 조금씩 밀림 · 매번 다른 폭 · 단조 하강
android              시작과 끝이 **똑같은 폭**으로 밀림 · id 대역이 통째로 다름
                       old-id→new-id   같은 오프셋
```

**폭이 상수다.** 드리프트면 매번 달라야 한다. 그리고 `event_id` 대역이 통째로
건너뛴다 — 다른 수집 세션이라는 뜻이다.

수집 시각으로 확인했다:

중복은 한 번의 동기화 배치에 몰렸고, 몇 가지 고정된 시간차로 나뉘었다. 개인별 날짜·
건수·시간차 분포는 공개본에서 제거했다.

즉 **8월 이력을 09-04 에 세 배치로 다시 넣은 것**이다. 배치마다 시계 보정 폭이 상수로
달라서 `(bucket_id, ts)` PK 가 못 걸렀다.

★ **그래서 폰 앱은 고칠 것이 없다.** 상시로 중복을 만들고 있는 게 아니라 재수입의
  흔적이고, 앞으로는 저장 관문이 같은 모양을 흡수한다.
  *"비슷하게 생겼으니 같은 원인"* 으로 넘어갔으면 엉뚱한 곳을 고칠 뻔했다 —
  이 저장소가 이미 아는 부류다(0027 자신의 첫 진단이 그래서 틀렸다).

## 곁가지 — 반환값이 거짓말을 하기 시작했다

흡수기가 **이미 저장된 행을 지우므로** insert 횟수를 세던 `upsert_events` 의 반환값이
실제 행 수보다 커졌다. `test_synthetic` 이 잡았다(2,042 를 돌려주는데 행은 2,033).
흡수한 수를 빼서 *"저장한 수"* 라는 계약을 지켰다.

## 방어

`tests/test_aw_sync.py` 에 다섯: 드리프트 모양이 합쳐진다 · **맞닿는 것은 안 합친다** ·
**내용이 다르면 겹쳐도 안 합친다** · **0초는 안 건드린다** · 버킷이 안 섞인다.

기대값을 하나 **뒤집었다**. `test_event_id_가_없으면_손대지_않는다` 는
*한계를 적어 둔 것*이지 원하는 동작이 아니었다 — id 가 없다는 이유로 눈에 보이는
중복을 못 고칠 이유가 없다.

## 교훈

**상류의 버그를 우리 표에서 고칠 때는, 우리가 아는 사실로 판정해야 한다.**
`event_id` 는 상류의 개념이라 상류가 바꾸면 같이 무너진다.
*"같은 창이 겹쳐 있을 수 없다"* 는 우리가 아는 사실이고, 상류가 무엇을 하든 참이다.
