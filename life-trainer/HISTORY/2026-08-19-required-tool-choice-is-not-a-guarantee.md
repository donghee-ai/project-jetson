# "롤체가 뭐야?" 에 활동 요약을 읽고 지어냈다 — `tool_choice="required"` 는 보장이 아니었다

- **발견**: 사용자가 Slack 에서 실제로 물어보고 스크린샷을 보냄. 08-18 에 "고쳤다"고
  적은 바로 그 질문이다.
- **증상**:

  ```
  사용자    예시 용어가 뭐야?
  봇        예시 용어는 사용자의 활동 분석 도구로, 오늘의 주요 활동은
            **작업 A**가 가장 많았고, 작업 B가 뒤를 이었습니다.
            (출처: 활동 요약)
  ```

  **주입된 오늘 활동 요약을 읽고 모르는 용어의 정의를 지어냈다.** 출처까지 붙여서.

## 원인 — 세 겹이었다

### 1. 서비스가 옛 코드로 돌고 있었다 (직접 원인)

`lifetrainer-slack` 이 11:46 에 기동됐고 `web_search`·트리거 확장은 13:55~14:02 에
들어갔다. **파일을 고쳐도 상주 서비스는 안 바뀐다.** 재기동 전까지 이 기기는
"검색 기능이 없는 버전"이었다.

### 2. `tool_choice="required"` 가 첫 바퀴 툴 호출을 보장하지 않는다 (진짜 원인)

08-18 진행 기록에 이렇게 적혀 있다:

> **`tool_choice="required"`**: 웹 트리거가 걸린 턴은 **첫 바퀴에 툴 호출 강제**.
> llama.cpp 가 지원하는 것을 실측 확인했다.

**틀렸다.** 실측(2026-08-19, llama.cpp `b1-a94d563`):

| 조건 | finish_reason | tool_calls |
|---|---|---|
| 툴 1개 + 짧은 프롬프트 | tool_calls | ✅ 호출 |
| 툴 6개 + 시스템 프롬프트, `max_tokens=400` | **tool_calls** | ✅ 호출 — 단 **본문을 먼저 쓴 뒤** |
| 같은 조건, `max_tokens=80~120` | **length** | ❌ **없음** |

llama.cpp 는 본문 생성을 막지 않는다. 모델은 **틀린 답을 300토큰 쓰고 나서** 툴을
부른다. 그 프로즈는 버려지지만 생성 8~9 tok/s 라 **35초가 그냥 날아가고**,
예산이 먼저 끝나면 툴 호출은 아예 안 나오고 **그 틀린 프로즈가 답이 된다.**

08-18 의 "확인"은 툴이 하나뿐인 상황이었을 것이다. 모델이 어차피 부를 케이스에서는
`required` 가 있으나 없으나 결과가 같다 — **차이가 없는 조건에서 확인한 셈이다.**

### 3. 주입 문장으로도 안 막혔다

`[웹 검색 불가] 추측하지 말고 확인하지 못했다고 답한다.` 를 user 메시지에 넣어봤다.
8B 는 그걸 무시하고 이번엔 **"롤체는 인공지능 모델의 파라미터를 조정하는 기술"**
이라고 답했다. 지어내는 대상만 바뀌었다.

## 수정 — 세 가지 층위

1. **선주입**: 웹 트리거가 걸리면 `converse` 가 **검색을 먼저 돌려** 결과를 ③층에
   싣는다. 툴 한 바퀴(8~20초)가 통째로 사라지고, 모델은 사실을 손에 쥔 채 시작한다.
2. **구조적 거절**: 검색 키가 없고 사용자가 주소를 준 것도 아니고 툴 설명에 주소가
   박힌 출처(깃허브 트렌딩 등)도 아니면 — **모델을 아예 부르지 않고** "확인하지
   못했다 + 키 넣는 법" 을 반환한다. 0.0초. 닿을 방법이 구조적으로 없는 질문에
   모델을 부르는 것 자체가 환각 생성 행위다.
3. **`required` 축소**: 사용자가 URL 을 직접 준 턴에만 남겼다. 그때는 열어야 할
   대상이 명확해 프로즈 낭비가 문제되지 않는다.

실측 (키 없는 상태):

```
"롤체가 뭐야?"          0.0초  · 거절 + 키 넣는 법        (기존 41초, 지어냄)
"깃허브 트렌딩 1위?"    15.9초 · fetch_url 로 실제 답      (기존 그대로 동작)
"오늘 뭐 했지?"         5.5초  · 내 기록으로 답            (영향 없음)
```

## 방어

`tests/test_websearch.py` 6건. 그중 두 개가 핵심이다:

- `test_refuses_without_calling_llm_when_no_search_and_no_url` — LLM 클라이언트를
  **불리면 실패하는 가짜**로 넣는다. 모델을 부르는 순간 테스트가 깨진다.
- `test_refusal_disappears_once_a_key_exists` — 이 거절 분기가 **임시 방편**임을
  못박는다. 키가 하나라도 있으면 죽는 코드다.

## 교훈

**1. 상주 서비스는 파일을 고쳐도 안 바뀐다.** 실기기 확인 전에 `systemctl restart`
와 기동 시각 확인을 먼저 한다. 이 프로젝트는 이제 상주 서비스가 4개다.

**2. "지원한다"와 "내가 원하는 것을 보장한다"는 다르다.** llama.cpp 는 `required` 를
지원한다 — 툴 호출이 **언젠가는** 나온다. 우리가 필요했던 것은 "본문보다 먼저"였고
그건 보장되지 않았다. 기능 이름이 아니라 **필요한 성질**을 실측해야 한다.
확인할 때는 **차이가 드러나는 조건**을 골라야 한다 (툴 1개짜리 테스트는 무의미했다).

**3. 프롬프트로 세 번 막으려 했고 세 번 실패했다.** 08-18 에도 "온도를 낮추니 오히려
악화" 를 겪었다. 이 기기의 8B 에게 지시문은 방어가 아니다. **구조로 막는다** —
정보를 주입하거나, 아예 부르지 않거나.
