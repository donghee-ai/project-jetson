# 패치가 옆 함수에 떨어져서, 수정하면 지워지는 상태가 됐다

- **발견**: 사용자가 웹에서 계획을 지우려다 `삭제 실패: 계획을 찾을 수 없습니다:
  id=134` 를 봤다. **나는 그 버그를 이미 고쳤다고 보고했었다.**

- **증상**: 두 가지가 동시에.
  1. 삭제가 여전히 안 된다 (고쳤다고 한 것이 안 고쳐졌다)
  2. ★ **수정(PATCH)을 하면 계획이 지워진다** — 아무도 아직 안 밟았다

- **원인**: 문자열 치환이 **첫 번째 일치**를 물었다.

  ```python
  old = '''            if get_plan(conn, plan_id) is None:
                  abort(404, description=f"계획을 찾을 수 없습니다: id={plan_id}")'''
  s.replace(old, new, 1)     # ← api_plan_update(908줄) 에 떨어졌다
  ```

  같은 두 줄이 `api_plan_update` 와 `api_plan_delete` 에 **똑같이** 있었다.
  `delete` 를 고치려고 쓴 코드(인스턴스를 archive 하고 `deleted: true` 를 반환)가
  `update` 안에 들어갔다. 그래서 **템플릿 없는 계획을 수정하려 하면 지워진다.**

  `grep -n` 으로 확인하지 않고 "패치 성공" 출력만 믿었다.

- **수정**: `update` 는 템플릿이 아니면 400 을 낸다(반복 규칙이 없으니 고칠 것이
  없다). `delete` 가 인스턴스를 지운다. 실기기 확인: `DELETE /api/plan/134` →
  `{"archived":1,"deleted":true}`.

- **방어**: 없다 — 웹 API 단위 테스트가 아직 이 경로를 안 덮는다.
  `tests/test_web.py` 에 넣을 자리다. **지금은 실기기 확인뿐이다.**

- **교훈**: **여러 곳에 같은 문자열이 있는 코드에 `replace(..., 1)` 을 쓰지 마라.**
  치환 뒤에 **어디에 떨어졌는지 확인**해야 한다 — `grep -n` 한 줄이면 됐다.

  더 나쁜 것은, 그 결과가 **조용한 데이터 파괴**였다는 점이다. 삭제가 안 되는 것은
  사용자가 보지만, 수정하면 지워지는 것은 **성공 응답과 함께** 일어난다.
  이 저장소가 오늘만 다섯 번째로 만난 "조용히 다르게 동작하는 것"이고,
  그중 세 번이 내 코드였다.
