# 해롭지 않다고 판정한 스왑이 이틀 뒤 기기를 죽였다

- **발견**: 08-31 07:03 일일 점검이 `❌ OOM` 을 냈다. 파 보니 **08-30 18:12 에
  전역 OOM 이 `llama-server`(8B)를 죽였다.** cgroup 한도가 아니라
  `constraint=CONSTRAINT_NONE, global_oom` — 기기 전체가 램+스왑을 다 썼다.

- **증상**: 주 모델 서버가 죽고 재시작. 그 사이 Slack 대화·에이전트·야간 배치가
  전부 불가. 커널이 남긴 그 순간의 표:

  ```
  llama-server 8B   RSS 6,577 + 스왑 5,719 = 12,296MB   ← 혼자 12.3GB
  llama-embed       RSS 2,020 + 스왑     0              ← MemorySwapMax=0 은 작동했다
  나머지 107개      RSS 거의 0 — 전부 스왑으로 밀려나 있었다
  스왑              7,833 / 8,009MB (97.8%) · 여유 52MB
  ```

- **원인**: **08-29 에 "이 스왑은 해롭지 않다"고 판정하고 손대지 않기로 한 것이
  틀렸다.** 그날 잰 것은 이랬다:

  ```
  pswpout 2,453MB · pswpin 15MB          되읽기 0.6%
  9시간 반 만의 첫 디코드                 되읽은 양 8.8MB · 해제 5~10ms
  ```

  **관측은 전부 맞았다.** 되읽기는 지금도 낮고, `llm_call` 의 `summarize_doc`
  평균 지연은 8B 가 9 → 12.3GB 로 자란 구간에도 19~20초로 평평하다.
  **자라는 것은 정말로 "할당됐지만 거의 안 건드리는" 페이지다.**

  틀린 것은 **거기서 물음을 멈춘 것**이다. *"이 2.3GB 가 지금 해로운가"* 만 묻고
  *"이게 계속 커지는가"* 를 안 물었다. **한 시점의 스냅숏으로 추세를 판정했다.**

  ```
  08-29 15:00  RSS 6,712 + 스왑 2,336 =  9,048MB   ← "차가운 페이지다. 손대지 마라"
  08-30 18:12  RSS 6,577 + 스왑 5,719 = 12,296MB   ← +3,248MB / 27시간
  ```

  차가운 페이지는 **지연을 안 만들지만 자리는 그대로 먹는다.** 되읽기율은
  *"얼마나 아픈가"* 를 재는 자이고, *"얼마나 커지는가"* 를 재는 자가 아니다.
  나는 아프지 않다는 것을 확인하고 **안전하다고 결론냈다.**

  두 번째로 틀린 것: **`OOMScoreAdjust=-200` 이 지켜 줄 것이라 믿었다.**
  그건 점수를 낮출 뿐 면제가 아니다. 8B 가 압도적 1위면 그래도 선택된다.
  실제로 `-200` 을 달고 죽었다.

  ★ 그리고 **재료가 없었다.** 8B 크기 이력이 남은 것은 커널이 OOM 표를 찍은
  **그 한 점뿐**이었다. `heartbeat` 는 헬스만 보고, `host-status` 는 `free` 를
  화면에 찍고 버린다. 사고가 나야만 관측되는 값이었다.

- **수정**: 매일 06:10 에 8B 를 재기동한다
  (`operate/systemd/llama-server-restart.timer` · `operate/tools/restart-llama-server.sh`).

  - **왜 재기동인가** — 자라는 것이 차가운 페이지라 `swappiness` 나
    `MemorySwapMax` 로는 안 잡힌다(막으면 안 쓰는 메모리를 램에 붙잡는다).
    `MemoryMax` 를 걸면 8B 자신이 죽는데, 로드가 10~30초라 임베딩과 달리
    자가재시작의 대가가 크다. **주기적으로 비우는 쪽이 값싸다.**
  - **왜 06:10 인가** — 05:50 야간 창 종료(실측 3~6분) 뒤, 06:20 백업 전.
  - **게이트웨이도 같이 올린다** — `openclaw-gateway` 가
    `Requires=llama-server.service` 라 같이 내려가는데, 의존이 끊겨 내려간 것은
    `Restart=always` 가 반드시 되살려 주지 않는다.
  - **재기동 전 크기를 CSV 로 남긴다** — 위 ★ 의 재료 부재를 고치는 줄이다.
    매일 한 점씩 쌓이면 다음에는 "선형인가 수렴인가" 를 물어볼 수 있다.

  첫 실행 실측 (08-31 09:32, 가동 15시간):

  ```
  8B        8,605MB → 6,818MB    −1,787MB
  기기 가용  3,221MB → 4,918MB    +1,697MB
  ```

  ★ **단발 재기동 한 번이 08-29 최적화 전체(지속 회수 256MB)보다 컸다.**

  > **★ 같은 날 저녁 추가 — 원인이 정밀해졌다.**
  > 이 문서는 처음에 8B 가 **시간에 따라** 자란다고 읽었다(추정 130MB/h).
  > 실제로 세어 보니 **요청이 변수다** — 요약 1건당 70~105MB 이고,
  > 호출 0건인 구간(08-30 06:10~18:12)에는 안 자란다.
  > `0018`(임베딩, 실문서 1건당 약 29MB)과 **같은 병**이었다.
  > 그래서 02:00 재기동을 야간 배치(02:10) **직전**에 둔 것이 우연히 맞았다 —
  > 하루치 증가의 대부분이 그 10분 뒤에 일어난다.
  > 남은 것과 대책 후보는 [`issues/0019`](../docs/issues/h-0019-the-8b-server-grows-about-eighty-megabytes-per-request.md).

- **방어**: 자동 검사는 없다 — 운영 설정이고 하루 한 번 도는 일이다.
  대신 **관측을 붙였다**: `llama-server-size.csv` 가 매일 한 점씩 쌓이고,
  `operate/tools/host-status.sh` 가 이미 OOM 을 세고 있어 재발하면 일일 점검이 잡는다.

- **교훈**: **"지금 해로운가" 와 "계속 커지는가" 는 다른 질문이다.**

  이 저장소는 *"살아 있다 ≠ 서빙 가능하다"*, *"툴을 불렀다 ≠ 일을 했다"*,
  *"끄는 플래그를 줬다 ≠ 꺼졌다"* 를 안다. 여기에 하나 더 붙는다 —
  **"지금 안 아프다 ≠ 안전하다."**

  → 자원 판정은 **한 점이 아니라 추세로** 한다. 스냅숏으로 "괜찮다"를 낼 때는
    **그 값이 시간에 따라 어떻게 변하는지 재는 자를 같이 붙인다.**
    없으면 그 판정은 다음 관측 때까지만 유효하다.

  그리고 **점수를 낮추는 설정은 면제가 아니다.** `OOMScoreAdjust`·`nice`·
  `ionice` 처럼 *우선순위*를 바꾸는 것은 **최악의 경우에 지켜 주지 않는다.**
  지켜야 하면 상한(`MemoryMax`)이나 회수(재기동)처럼 **양을 정하는 수단**을 쓴다.

  > **08-29 의 조치는 그대로 옳다.** 임베딩 CUDA 제거는 야간 배치 OOM 을
  > 5회 → 1~2회로 줄였고(08-30 121건 1회 · 08-31 128건 2회, 실패 0),
  > zram 판정도 여전히 맞다. **틀린 것은 8B 쪽을 "손대지 마라"로 닫은 것**이다.
