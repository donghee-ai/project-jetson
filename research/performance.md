# 벤치마크 실측 결과 — Jetson Orin NX 16GB

> 측정일: 2026-08-14 / 측정 조건: MAXN, llama.cpp `b1-a94d563`, CUDA 12.6
> 관련: [llm-runtime.md](../docs/llm-runtime.md) · [hardware.md](hardware.md)

---

## 0. 핵심 요약 — 세 줄

1. **표준 벤치마크 수치는 실사용 성능이 아니다.** `llama-bench`의 14.22 tok/s는
   빈 컨텍스트 값이며, 깊이 32K에서는 **3.96 tok/s**로 70% 떨어진다.
2. **IQ2_M(2.7비트) 품질은 예상보다 훨씬 좋다.** JSON 구조화 출력, 조건 대조 추론,
   장거리 검색(10/10)을 모두 통과했다.
3. **32K 컨텍스트는 안전하다.** OOM 없이 전 구간 RAM 14.4 GB로 안정적이었고,
   한도 초과 시 서버가 죽지 않고 HTTP 400을 반환했다.

## 2. 메모리 대역폭 (모든 예측의 기준값)

측정 도구: [`scripts/membw.cu`](../scripts/membw.cu)

```
사양치 (LPDDR5 128-bit)      102.4 GB/s
실측 순차 읽기                60.0 GB/s   ← 사양 대비 58%
실측 D2D 복사 (읽기+쓰기)     69.5 GB/s
```

측정 중 GPU 918 MHz 도달, VDD_IN 11~13 W, tj 61°C — **전력·발열 제한이 아니다.**
단일 클라이언트(GPU)로 메모리 컨트롤러를 포화시키지 못하는 구조적 한계로 보인다.

**LLM 토큰 생성은 대역폭이 천장이므로 이 60 GB/s가 모든 성능 예측의 출발점이다.**

## 3. 모델 비교 — llama-bench (빈 컨텍스트)

```bash
llama-bench -m <model> -ngl 99 -p 512 -n 128 -fa 1 -r 2
```

| 모델 | 크기 | 파라미터 | pp512 | tg128 | 전력 | 온도 |
|---|---|---|---|---|---|---|
| Qwen3-8B Q4_K_M | 4.68 GiB | 8.19 B (덴스) | **353.74 ± 5.66** | 11.14 ± 0.01 | 20.4 W | 67°C |
| **Qwen3-30B-A3B IQ2_M** | 9.71 GiB | 30.53 B (MoE) | 264.26 ± 4.16 | **14.22 ± 0.02** | 12~14.7 W | 59~61°C |
| 차이 | +107% | +273% | **−25%** | **+28%** | −32% | 더 낮음 |

### MoE 가설 — 확인되었으나 예측보다 약함

**30B-A3B가 8B보다 토큰 생성 28% 빠르다.** 파라미터가 3.7배 큰 모델인데도.

다만 예측(약 21 tok/s)에는 못 미쳤다. 실측 14.22에서 역산하면 **토큰당 3.7~4.2 GB**를
읽는다. "활성 3.3B / 총 30.5B" 비율로 추정한 2.5 GB보다 크다.

| 원인 | 설명 |
|---|---|
| **어텐션은 희소하지 않다** | MoE로 분할된 것은 FFN뿐. 48개 레이어의 어텐션·임베딩·출력 레이어는 매 토큰 전부 읽는다 |
| **랜덤 액세스 패널티** | 전문가 선택이 토큰마다 바뀌므로 순차 읽기가 아니다. 실측 60 GB/s는 순차 기준 |

### 프롬프트 처리는 MoE가 불리 (−25%)

프리필에서는 512토큰 배치가 여러 전문가를 두루 활성화하여 연산량이 증가한다.
**긴 입력 / 짧은 출력**이면 이 손해가 생성 이득을 상쇄한다.

### 시간 비용 모델

측정값에 잘 맞는 근사식:

```
토큰당 시간(초) ≈ 0.073 + 6.0e-6 × 컨텍스트_깊이
```

깊이 0에서 약 13.7 tok/s, 이후 깊이에 비례해 선형으로 느려진다.

### 왜 생성만 느려지는가

| | 깊이 영향 | 이유 |
|---|---|---|
| 프롬프트 처리 | 작음 | GPU 연산을 병렬로 소화 |
| **토큰 생성** | **큼** | 매 토큰마다 **KV 캐시 전체를 순차 읽기** → 깊이에 비례해 메모리 트래픽 증가 |

> ⚠️ **프롬프트 속도 수치 해석 주의.** 서버가 이전 요청의 프리픽스를 캐싱하므로
> 표의 값은 **새로 추가된 토큰만** 처리한 속도다. 매번 새 문서를 넣는 실제 배치
> 작업에서는 이보다 낮게 나올 수 있다.

### 장거리 검색 — 10/10 완벽

문서 80개(31,901토큰) 속에 묻힌 **맨 앞** 공고의 정보를 전 구간에서 정확히 찾아냈다.
**IQ2_M 양자화가 장거리 어텐션을 손상시키지 않았다.**

## 5. 품질 검증 — 실제 대화 7단계

측정 도구: [`scripts/chat-bench.py`](../scripts/chat-bench.py)
지원사업 공고를 투입한 뒤 실무에서 요구되는 작업을 순차 수행.

| 단계 | 항목 | 깊이 | 생성 | 결과 |
|---|---|---|---|---|
| W1 | 인사 | 26 | 12.71/s | 정상 |
| W2 | 문서 요약 | 911 | 12.81/s | ✅ 정확 |
| W3 | 정보 추출 | 1,060 | 12.54/s | ✅ 마감일·금액 정확 |
| **W4** | **JSON 출력** | 1,197 | 12.51/s | ✅ **7개 필드 전부 정확** |
| **W5** | **자격 판정** | 1,361 | 12.24/s | ✅ **함정 통과** |
| W6 | 긴 생성 | 1,428 | 12.27/s | ✅ 평가기준 정확 재현 |
| W7 | 지시 이행 | 1,628 | 11.92/s | ✅ 정확히 5단어 |

### W4 — JSON 구조화 출력 (핵심 검증)

설명 문장 없이 순수 JSON만, 스키마 준수, 날짜 형식 변환까지 정확.

```json
{"사업명":"2026년 인공지능 기반 스마트 제조혁신 기술개발사업","접수시작":"2026-03-02",
 "접수마감":"2026-04-15","연간최대지원금_억원":5,"최소업력_년":3,
 "매출하한_억원":10,"매출상한_억원":300}
```

### W5 — 조건 대조 추론 (함정 문항)

공고 요건은 "업력 3년 이상", 질문은 "업력 2년". **지원 불가가 정답.**

> "지원 불가능합니다. 업력이 3년 미만이기 때문입니다."

매출 15억이 요건(10~300억)을 만족한다는 것까지 감안해 업력만 지적했다.

### ⚠️ 사전 예측이 틀렸음을 기록

착수 전 여러 차례 **"IQ2_M은 포맷 준수와 지시 이행에서 먼저 무너진다"** 고 예측했으나,
**실측에서는 그런 징후가 없었다.** grant-radar가 요구하는 작업 유형(구조화 추출,
조건 대조, 정확한 형식 준수)을 모두 통과했다.

> 단, 각 항목 **1회 측정**이므로 통계적 견고성은 없다. 운이 좋았을 가능성 배제 불가.

## 6. 한국어 토크나이저 효율

동일 의미 문장을 각 언어로 토큰화. `/tokenize` 엔드포인트 사용.

| 언어 | 토큰 | 문자 | 문자당 토큰 | 영어 대비 |
|---|---|---|---|---|
| 중국어 | 20 | 47 | 0.426 | 0.69배 |
| **영어** | **29** | **200** | **0.145** | **기준** |
| 일본어 | 42 | 59 | 0.712 | 1.45배 |
| **한국어** | **45** | **75** | **0.600** | **1.55배** |

**한국어는 같은 내용에 토큰이 55% 더 든다.** Qwen3는 119개 언어 지원을 표방하고
한국어도 공식 목록에 있으나, 토크나이저는 중국어에 최적화되어 있다.

| 컨텍스트 32K에 담기는 분량 | |
|---|---|
| 한국어 | 약 54,000자 (A4 28~34쪽) |
| 영어 | 약 226,000자 (약 2.4배) |

## 7. 실무 기준표

### 입력 길이별 권장

| 입력 길이 | 생성 속도 | 체감 | 용도 |
|---|---|---|---|
| ~2K | 12~13 tok/s | 쾌적 | 대화, 짧은 질의 |
| **3~5K** | **10~11 tok/s** | **실용 — 권장 구간** | **문서 1건 처리** |
| 8~16K | 6~8 tok/s | 느리지만 견딤 | 여러 문서 비교 |
| 22~32K | 4~5 tok/s | 배치 전용 | 대량 투입 |

### grant-radar 유형 환산 (입력 3,000 / 출력 300 토큰)

```
프롬프트  3,000 ÷ 237  = 12.7초
생성        300 ÷ 10.9 = 27.5초
──────────────────────────────
건당 약 40초  →  하루 100건 = 1시간 7분
```

> 초기 추정(35초)은 빈 컨텍스트 속도(14.22 tok/s) 기준이었다.
> **깊이 3K의 실측(10.92 tok/s)을 적용하면 40초로 15% 늘어난다.**

### 파이프라인 설계 지침

**입력을 3~5K로 끊는 것이 처리량에 유리하다.** 긴 문서는 청킹해서 여러 번 호출하는
편이, 한 번에 32K를 밀어넣는 것보다 총 처리 시간이 짧다.

예: 30K 문서 1회 처리(3.96 tok/s) vs 3K씩 10회(10.92 tok/s) — 후자가 약 2.7배 빠르다.

## 8. 메모리 안정성

| 구간 | RAM 사용 | 여유 | 스왑 |
|---|---|---|---|
| 서버 기동 직후 | 11.8 GB (RSS) | — | 0 |
| 전 측정 구간 | **14,414~14,445 MB** | 862~902 MB | 24 MB |
| 컨텍스트 한도 초과 시 | 14,432 MB | 896 MB | 24 MB |

**전 구간에서 RAM이 14.4 GB로 안정적이었고 OOM은 발생하지 않았다.**
llama.cpp가 KV 캐시를 기동 시 전량 할당하므로 깊이가 늘어도 추가 할당이 없다.

한도(32,768) 초과 요청은 **HTTP 400으로 거부되며 서버는 죽지 않는다.**

## 9. 재현 방법

```bash
# 메모리 대역폭
/usr/local/cuda/bin/nvcc -O3 -o /tmp/membw scripts/membw.cu && /tmp/membw

# 표준 벤치마크 (빈 컨텍스트)
~/llama.cpp/build/bin/llama-bench -m ~/project/project-jetson/models/<모델>.gguf \
  -ngl 99 -p 512 -n 128 -fa 1 -r 2

# 품질 + 얕은 깊이 (서버 실행 중이어야 함)

# 컨텍스트 깊이별 (문서 개수 지정)
python3 scripts/deep-context-bench.py 1,2,4,8,12,16
```
