## 0. 결론 먼저

**제안: 큰 모델(VLM)이 작은 모델(검출기)을 현장에서 자동으로 가르치는 폐루프 카메라 시스템.**

```
선생 (GPU, 느림, 똑똑함)   VLM이 장면을 보고 라벨을 쓴다        ← 사람 라벨링 0
       ↓ 라벨 축적
학생 (DLA, 빠름, 상시)      현장 전용 검출기가 24시간 돈다        ← 점점 정확해진다
       ↑ 불확실한 것만 선생에게
```

세 가지 이유로 **이 구조는 젯슨에서만 성립한다.**

| | 근거 |
|---|---|
| 선생·학생 **동시 상주** | 16 GB 통합 메모리 — dGPU처럼 PCIe 복사 없음. DLA가 학생을 돌리는 동안 GPU가 선생을 돌린다 |
| **24시간 학습이 전기료로 가능** | 실측 유휴 4.6 W / 부하 20.4 W. RTX 데스크톱(200 W+)으로는 상시 가동이 비현실적 |
| **라벨링을 남에게 맡기지 않음** | 자동 라벨링을 클라우드에 맡기면 영상 전량을 업로드해야 한다 (1080p30 1대 = 월 1.6 TB) |

## 2. ★ 레퍼런스 재조사 — 기존 계획의 전제가 낡았다

[vision-agent-plan.md](vision-agent-plan.md)는 "Frigate는 객체 검출까지만 하고 그 위층(VLM 이해·자연어 검색)이 비어 있다"를 전제로 한다.
**클론된 Frigate 소스를 직접 열어본 결과, 그 층은 이미 채워져 있다.**

| 기능 | 증거 (`refs/reference/frigate`) |
|---|---|
| GenAI 이벤트 설명 | `frigate/genai/` — `manager.py`, `prompts.py`, `plugins/` |
| **llama.cpp 직접 연동** | `frigate/genai/plugins/llama_cpp.py` — 스트리밍·툴콜 파싱까지 구현됨 |
| 다른 백엔드 | `ollama.py`, `gemini.py`, `openai.py`, `azure-openai.py` |
| **다중 프레임 위협도 판정** | `prompts.py: build_review_description_prompt()` — 시퀀스 분석 + `potential_threat_level` 0/1/2 + 한국어 출력 옵션 |
| 시맨틱 검색 | `frigate/embeddings/`, `docs/.../semantic_search.md` |
| 얼굴 인식 · 번호판 | `face_recognition.md`, `license_plate_recognition.md` |
| 커스텀 분류기 학습 | `custom_classification/` — MobileNetV2, TensorFlow 2.19 (aarch64 휠 포함) |
| **젯슨 DLA 검출** | `object_detectors.md:587` — `YOLO_MODELS=yolov7-320-dla`, **DLA0만 지원**, 미지원 레이어는 GPU 폴백 |

> **즉, "Frigate 위에 VLM 캡션 레이어를 얹는다"는 이미 구현된 기능을 다시 만드는 일이다.**
> 오히려 우리가 만든 llama-server를 `genai` 프로바이더로 꽂으면 하루면 끝난다.

### 그래서 진짜 남은 빈틈

Frigate의 커스텀 분류기 문서를 끝까지 읽으면 결정적인 문장이 나온다.

```
"You'll be guided through each class one at a time to select which images represent that class."
                                    ↑ 사람이 손으로 라벨링한다
```

정리하면 이렇다.

| Frigate가 하는 것 | Frigate가 **안 하는 것** |
|---|---|
| VLM으로 이벤트를 설명 (일회성 텍스트) | 그 설명을 **학습 라벨로 재활용** |
| 커스텀 분류기 학습 지원 | **라벨을 자동으로 만들어 주는 것** (사람 필수) |
| 고정 모델(COCO 80클래스) 검출 | **현장 전용 어휘**로 검출기를 진화시키는 것 |
| 이벤트 단위 설명 | 시간·카메라를 가로지르는 **누적 학습** |

**빈틈은 "위층"이 아니라 "루프"다.** 아무도 선생과 학생을 한 기계에 넣고 돌리지 않았다.

## 3. 제안 — Understudy (대역 배우)

> 이름 그대로 **under-study**: 작은 모델이 큰 모델 밑에서 배워 결국 그 역할을 대신한다.

### 3-1. 한 줄 정의

**카메라 앞에 두면, 큰 VLM이 며칠에 걸쳐 작은 검출기에게 "이 현장"을 가르쳐서,
결국 GPU 없이 DLA만으로 현장 전용 인식이 돌아가게 만드는 장치.**

### 3-2. 왜 이게 새로운가

| 기존 | 한계 |
|---|---|
| Frigate 커스텀 분류 | 사람이 라벨링. 분류만(검출 아님) |
| Autodistill 류 "대형→소형 증류" | 데스크톱/배치 중심, 클라우드 전제 — **연속 루프 아님** (※ 조사 미완, §7) |
| 클라우드 자동 라벨링 | 영상 전량 업로드 필요 — 프라이버시·비용에서 탈락 |
| dusty-nv `nanoowl` / `nanodb` | 훌륭한 **부품**. 루프로 엮은 사례는 없음 |

**"현장에서, 사람 없이, 데이터를 내보내지 않고, 계속 좋아지는 인식기"** 는 비어 있다.

### 3-3. 아키텍처

```
IP캠 RTSP ─→ Frigate  [NVDEC 디코딩 · 모션 · 이벤트 · 녹화 · UI · MQTT]   ← 그대로 씀
                 │
                 ├─→ ① 학생 추론 (DLA)  현장 전용 모델, 상시, 저비용
                 │        │
                 │        ├─ 확신함 → 그대로 이벤트 발행 (선생 호출 없음)  ← 대부분
                 │        └─ 불확실/신규 ─┐
                 │                        │  + OFA 신규성 게이트 + 무작위 10% 강제 샘플
                 ▼                        ▼
        ② 선생 VLM (GPU, llama.cpp mtmd)  "무엇이 보이는가 / 이것은 무엇인가"
                                          → 구조화 JSON 라벨
                 │
                 ▼
        ③ 라벨 저장소 (SQLite + 이미지)   합의 규칙·신뢰도 임계·사람 검수 큐
                 │
                 ▼
        ④ 야간 학습 잡 (선생 언로드 후)   학생 갱신 → 홀드아웃 회귀 검사 → 통과 시 배포
                 │
                 └──────────→ ① 로 되돌아감
```

### 3-4. ★ 학생 모델 사다리 — 싼 것부터 오른다

전부 파인튜닝부터 하면 실패한다. **비용 순서대로 3단**으로 올린다.

| 단계 | 학생 | 학습 비용 | 선생이 만드는 것 |
|---|---|---|---|
| **L0** | NanoOWL (개방어휘 검출, TensorRT) | **0** | **텍스트 프롬프트** — "택배 상자를 든 사람" |
| **L1** | CLIP 임베딩 + 선형 분류기 | **수초** | 임베딩에 붙일 클래스 라벨 |
| **L2** | MobileNetV2 / YOLO-n 파인튜닝 → DLA | 수분~밤새 | 이미지 + 박스 + 클래스 |

> **L0가 핵심 아이디어다.** 선생이 학생의 *가중치*가 아니라 *프롬프트*를 고쳐 쓴다.
> 학습 없이 오늘 바로 성능이 오르고, 실패해도 롤백이 텍스트 한 줄이다.
> L1은 몇 초 만에 학습되고 메모리를 거의 안 먹는다. L2는 마지막 수단.

### 3-5. 메모리 예산 (안전선 13.4 GB)

| 구성요소 | SmolVLM2 구성 | Qwen2.5-VL 7B 구성 |
|---|---|---|
| Frigate (ffmpeg 2대 + 검출 + 웹) | 1.5~2.5 GB | 1.5~2.5 GB |
| 학생 L0/L1 (NanoOWL + CLIP TRT) | ~0.8 GB (추정) | ~0.8 GB |
| 선생 VLM (Q4) | 1.5 GB | 5.5 GB |
| KV 캐시 + 연산 버퍼 | ~1.0 GB | ~1.0 GB |
| OS + 여유 | ~1.5 GB | ~1.5 GB |
| **합계** | **~7.3 GB ✅ 여유** | **~11.3 GB ⚠️ 빠듯** |

**야간 학습 잡은 선생을 언로드하고 실행한다.** 동시 상주는 금지.
[llm-models.md](../../measure/findings/llm-models.md)의 "텍스트 LLM을 따로 띄우지 말 것" 원칙 유지 — 텍스트 작업도 선생 VLM이 겸한다.

### 3-6. 시간 예산

측정치로 환산한다 ([performance.md](../../measure/findings/performance.md)).

```
선생 1회 = 이미지 프리필 + 캡션/라벨 100~150토큰
         ≈ 7~11초  →  시간당 상한 약 330~500건

가정집 현관 일일 이벤트 50~200건 중, 게이트를 통과해 선생에게 가는 것은 초기 100%,
학생이 배울수록 감소 → ★ "선생 호출률 하락 곡선"이 이 프로젝트의 성과 지표 그 자체다.
```

> **컨텍스트를 3~5K로 끊을 것.** 깊이 32K에서 3.96 tok/s(−70%)로 무너지므로,
> 이벤트 하나당 짧은 프롬프트로 처리한다. 누적 서사는 SQLite가 들고 LLM에 넣지 않는다.

## 4. 검증 계획 — 카메라 없이 시작

### Phase 0 — 성패를 가장 빨리 아는 3가지 (카메라 불필요, 비용 0)

- [ ] **선생 품질**: `llama-mtmd-cli` + SmolVLM2 2.2B로 정지 이미지 라벨링 → **JSON 스키마 준수율**
      (못 쓰면 여기서 중단. 캡션 감상문이 아니라 *라벨*이 나와야 한다)
- [ ] **선생 속도**: 이미지 1장당 실측 초 → 시간당 처리량 상한 확정
- [ ] ★ **DLA + GPU 동시 실행 시 대역폭 경합 측정** ← **생태계에 존재하지 않는 데이터**
      DLA에서 검출을 돌리는 동안 GPU의 tok/s가 몇 % 떨어지는가?
      (연산 자원은 분리돼 있지만 **60 GB/s 메모리는 공유**한다 — 이 설계의 최대 미지수)
- [ ] `sudo apt install docker.io docker-compose-v2`
- [ ] `bash measure/tools/thermal-test.sh 300` — 아직 미실행. 24시간 가동 주장의 근거

### Phase 1 — 파이프라인 (영상 파일로)

- [ ] Frigate를 파일 입력으로 구동, `jtop`으로 **NVDEC 사용률 > 0** 확인
- [ ] 우리 llama-server를 Frigate `genai` **llama_cpp 프로바이더로 연결** (이미 구현돼 있음 — 새로 만들지 말 것)
- [ ] NanoOWL(L0) 올려서 프롬프트만으로 현장 어휘 검출

### Phase 2 — 루프 폐쇄 (여기부터가 신규 개발)

- [ ] 게이트: 학생 신뢰도 + OFA 신규성 + **무작위 10% 강제 샘플**(탐색 편향 방지)
- [ ] 선생 라벨 저장소 + 합의 규칙 (Frigate의 "3회 중 60% 일치" 방식 차용)
- [ ] L1 선형 분류기 자동 학습 → 배포
- [ ] **홀드아웃 회귀 검사** — 나빠지면 자동 롤백 (모델 버저닝)

### Phase 3 — 성과 측정

- [ ] **선생 호출률 곡선** (1일차 → 7일차) ← 핵심 지표
- [ ] 오탐률 변화, 학생 지연(ms), 사람 검수로 본 라벨 정확도
- [ ] 24시간 전력·온도·메모리 안정성

### Phase 4 — 확장

- [ ] L2 파인튜닝 → DLA 배포
- [ ] Home Assistant 연동 (`ha-mcp` + 툴콜링 6/6 Qwen3-8B)

### 하드웨어

USB 웹캠(~2만원)으로 Phase 1~2까지 가능. **Phase 0은 아무것도 사지 않고 오늘 시작한다.**
24시간 운영 단계에서 RTSP IP캠(야간 IR·방수, 3~8만원)으로 교체.

## 6. 리스크

| 리스크 | 심각도 | 대응 |
|---|---|---|
| **선생 라벨이 틀림 (환각)** | **높음** | 합의 규칙 + 신뢰도 임계 + 사람 검수 큐. 라벨은 *제안*이지 진리가 아님 |
| **피드백 루프 편향** — 학생이 못 보는 건 선생도 안 봄 | **높음** | **무작위 10% 강제 샘플** (설계에 못 박을 것) |
| DLA+GPU 대역폭 경합으로 둘 다 느려짐 | **높음** | Phase 0에서 선측정. 심하면 선생을 야간 배치로 미룸 |
| 학생 성능 퇴행 | 중간 | 고정 홀드아웃 + 자동 롤백 |
| 메모리 초과 | 중간 | SmolVLM2로 시작. 학습 시 선생 언로드 |
| Frigate DLA0만 지원 / 레이어 폴백 | 중간 | DLA1은 학생 전용으로 직접 씀 (Frigate 밖) |
| 카메라 미보유 | 낮음 | Phase 0~1은 파일로 |

## 8. 차선안 — 이 제안이 무거우면

### 대안 A. 「Orin 이종 엔진 대역폭 스케줄러」 (인프라)

이 저장소의 최대 발견은 **"60 GB/s가 유일한 공유 자원"** 이다.
그렇다면 GPU/DLA/NVDEC 동시 실행은 연산 문제가 아니라 **대역폭 배분 문제**다.
엔진 조합별 경합 매트릭스를 실측해 공개 + 예산 기반 스케줄러 제공.

- 장점: 카메라 불필요, 이 프로젝트의 강점(정밀 측정)과 정확히 일치, 생태계에 데이터가 없음
- 단점: 제품이 아니라 도구. 사용자층이 좁음
- **→ Understudy Phase 0의 부속으로 흡수 가능. 별도로 갈 필요 없음**

### 대안 B. 한국어 온프레미스 문서·회의 어플라이언스

EXAONE 한국어 토큰 19% 절약 + `sherpa-onnx`/`whisper_trt`.
시장(병원·법률·공공은 클라우드 금지)은 확실하나 **젯슨의 비전 엔진을 하나도 쓰지 않는다.**
"젯슨의 강점"이라는 기준에서 탈락.
