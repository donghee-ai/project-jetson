# Grant Radar — 서울·경기 지원사업 통합 서비스 기획

> 작성일: 2026-08-13
> 상태: **기획 단계** (미착수) / 향후 사업화 검토 대상
> 관련: [hardware.md](../research/hardware.md)

---

## 1. 개요

**서울·경기 지역의 정부 지원사업 및 유관 공고를 통합해, 첨부파일에 묻힌 지원자격을
LLM으로 구조화하여 "내가 지원 가능한 것만" 걸러주는 정적 웹서비스.**

### 핵심 가설

> 지원사업 정보는 이미 여러 곳에 공개되어 있다.
> 사람들이 귀찮아하는 것은 **"찾는 것"이 아니라 "내가 되는지 확인하는 것"** 이다.
> 공고 50건을 열어 HWP를 내려받아 읽고 "아, 난 안 되네"를 반복하는 그 과정.

이 가설이 맞다면, 단순 취합이 아니라 **자격요건 매칭**이 제품의 본체다.

### 왜 이 아이템인가 (job-radar 대비)

| 항목 | job-radar | Grant Radar |
|---|---|---|
| 데이터 획득 | 기업 사이트 크롤링 8종 | **공식 오픈API** |
| 법적 지위 | 회색지대 (잡코리아-사람인 판례 불리) | **공공데이터, 상업적 이용 허용** |
| 크롤러 유지보수 | 사이트 개편 시마다 파손 | API 스펙 안정 |
| 사용자 동기 | 이직 시기에만 | **지원금 수천만~수억, 상시** |
| 재방문 이유 | 약함 | **강함 (신규 공고 계속 발생)** |
| 수익화 경로 | 좁음 | 광고 + 제휴 리드 |

job-radar의 최대 병목이었던 **본문 수집 문제가 API로 해결**된다.

## 2. 범위

### 지역: 서울 · 경기 한정

전국은 수천 건이다. 처음부터 넓히면 **정확도가 무너지고, 정확도가 무너지면 이 서비스는
존재 이유가 없다.** 서울·경기로 시작해 50~100건 규모에서 자격요건 추출 정확도를
100%에 가깝게 만드는 것이 우선.

넓히는 것은 나중에 쉽다. 파이프라인은 그대로 두고 소스만 추가하면 된다.

### 대상 공고 유형

- 창업지원 (예비창업 / 초기창업 / 도약)
- R&D 과제
- 자금·융자·보증
- 인력·교육
- 수출·판로
- 시설·공간 (입주공간, 테스트베드)

## 3. 데이터 소스

### 3-1. 공공 API — 1차 대상 ✅ 법적으로 안전

| 소스 | 제공 내용 | 확인 상태 |
|---|---|---|
| **기업마당 (bizinfo)** 지원사업정보 API | **중앙부처·지자체·유관기관 통합.** 분야(금융/기술/인력/수출/내수/창업/경영/기타), 사업명, 신청시작일, 신청종료일, 소관기관 | ✅ **API 존재 확인** |
| **K-Startup** 지원사업 공고 오픈API | 창업 분야 공고 | ✅ **공공데이터포털 등록 확인** |
| 공공데이터포털 기타 데이터셋 | 부처별 개별 제공 | ⚠️ 개별 확인 필요 |

기업마당이 이미 중앙+지자체를 통합하고 있어 **여기 하나로 상당 부분이 커버될 가능성**이 높다.
→ 착수 시 가장 먼저 확인할 것: 기업마당 API의 서울·경기 커버리지와 첨부파일 URL 제공 여부.

### 3-2. 지역 기관 — 2차 대상 ⚠️ 개별 확인 필요

아래는 **API 제공 여부 미확인**. 착수 시 각각 조사 필요.

| 기관 | 비고 |
|---|---|
| 서울경제진흥원 (SBA) | 서울시 중소기업·창업 지원 주관 |
| 서울창업허브 | |
| 경기도경제과학진흥원 (GBSA) | 경기도 주관 |
| 경기창조경제혁신센터 / 서울창조경제혁신센터 | |
| NTIS / IRIS | 범부처 R&D 과제 |
| TIPA · KEIT · KIAT | R&D 전문관리기관 |
| 주요 기초지자체 | 성남·수원·용인 등 |

### 3-3. ⚠️ 민간 사이트 취합 시 주의

**공공데이터가 아닌 민간 사이트를 크롤링하는 순간, job-radar에서 지적한 법적 리스크가
그대로 돌아온다.** 이 프로젝트가 job-radar보다 나은 가장 큰 이유가 "공공데이터라
상업적 이용이 허용된다"는 점인데, 민간 소스를 섞으면 그 장점이 희석된다.

원칙:
- **공공 API를 최우선으로 소진**한다. 기업마당이 이미 지자체를 통합하므로 상당 부분 해결될 것.
- 민간 소스는 **꼭 필요한 경우에만**, 개별적으로 ToS·robots.txt 확인 후 추가.
- 민간 소스 비중이 커지면 사업화 전 변호사 검토 필수.

## 4. 차별화 — 첨부파일 안의 정보

기존 서비스(기업마당, K-Startup, [kfund.ai](https://kfund.ai/), [THE VC](https://thevc.kr/grants))가
**모두 못 하고 있는 것**이 하나 있다.

```
공고 본문 (API 제공)  : 사업명, 신청기간, 소관기관        ← 다들 함
첨부 HWP/PDF          : 지원자격, 지원금액, 제출서류,      ← 여기가 진짜 정보
                        선정기준, 제외대상, 가점항목
                                ↓  LLM 추출
구조화 필드            : 업력범위, 매출한도, 지역, 업종코드,
                        인증요건, 지원금 상한, 자부담률
                                ↓
        사용자 프로필: "업력 2년 · 서울 · 제조업 · 매출 3억 · 법인"
                                ↓
                   ▶ 지원 가능 12건 / 불가 38건 (사유 표시)
```

**"단순 취합"으로는 차별화가 안 된다.** 기업마당이 이미 하고 있다.
**자격요건 매칭이 제품의 본체**이며, 이것이 LLM을 쓰는 유일한 이유다.

### 기술적 해자: HWP 파싱

한국 공공문서의 저주. 신형 HWPX는 XML 기반이라 다룰 만하지만 **구형 HWP는 파싱이 불안정**하고,
자격요건이 표 안에 들어있으면 난이도가 더 올라간다.

남들이 안 하는 이유가 여기 있고, 그래서 해자가 된다.

## 5. 아키텍처 — 정적 서비스

### 왜 정적으로 충분한가

공고는 하루 단위 갱신으로 충분하다. 실시간이 필요 없다.
목록·필터·상세·검색·마감 캘린더 — **전부 정적으로 가능**하다.

### 왜 정적이 오히려 유리한가 (광고 모델)

```
공고 1건  =  정적 페이지 1개
공고 수천 건  =  색인 가능한 페이지 수천 개
    → "청년창업사관학교 2026 신청자격"
    → "서울시 제조업 R&D 지원금 마감일"
    → 롱테일 검색어 유입  ← 광고 모델의 엔진
```

| 장점 | 설명 |
|---|---|
| **SEO** | 공고별 사전 렌더링 페이지 = 검색 유입 극대화 |
| **비용** | CDN 정적 호스팅. 트래픽 늘어도 **호스팅 비용 0** |
| **안정성** | 서버 장애 없음, 관리 부담 없음 |
| **광고 적합성** | 애드센스는 정적 페이지에 붙이기 쉬움 |

### 파이프라인

```
[ 일 1회 배치 ]
  기업마당 API ─┐
  K-Startup API ─┼→ 신규 공고 감지 (증분)
  지역기관 소스 ─┘        ↓
                    첨부파일 다운로드 (HWP/PDF)
                          ↓
                    파싱 → 텍스트 추출
                          ↓
                    LLM: 자격요건 구조화 추출
                          ↓
                    검증 (스키마 + 원문 근거 대조)
                          ↓
                    grants.json  +  공고별 정적 페이지 생성
                          ↓
                    정적 배포 (CDN)

[ 브라우저 ]
  사용자 프로필 입력 → 클라이언트 사이드 필터링 → 지원 가능 공고
```

LLM은 **빌드타임에만** 동작한다. 런타임 추론이 없으므로 서버가 필요 없다.

## 6. ★ 정확도 설계 원칙 (가장 중요)

job-radar와 결정적으로 다른 지점이다.

> 채용공고 요약이 틀리면 → 사용자가 짜증남
> **지원사업 마감일이 틀리면 → 사용자가 수억짜리 기회를 놓침**

LLM 환각이 **실질적 금전 피해로 직결**된다. 따라서:

| 원칙 | 구현 |
|---|---|
| **핵심 사실은 LLM이 생성하지 않는다** | 날짜·금액·기관명은 **API 원본 값만** 사용. LLM 출력으로 덮어쓰지 않음 |
| **추출만, 생성 금지** | LLM은 첨부파일에서 발췌만. 요약·추론·보간 금지 |
| **원문 근거 필수 저장** | 추출한 모든 필드에 출처 문장을 함께 저장. 대조 불가 시 폐기 |
| **스키마 강제** | 구조화 출력 강제, 파싱 실패 시 "미확인"으로 표시하고 넘어감 |
| **불확실은 침묵** | 애매하면 추측하지 말고 "원문 확인 필요"로 표시 |
| **원문 링크 최우선 노출** | 모든 페이지에 공식 공고 원문 링크를 크게 배치 |
| **면책 문구 명시** | "본 정보는 참고용이며 최종 확인은 공식 공고를 따르십시오" |

**"모르면 비워두는" 설계가 "그럴듯하게 채우는" 설계보다 무조건 낫다.**

## 7. 운영 설계

### 7-1. 일일 처리 부하 — 가볍다

서울·경기 한정 시 신규 공고는 **하루 최대 100건** 수준으로 추정.

| 단계 | 건당 | 100건 |
|---|---|---|
| API 호출 + 첨부 다운로드 | ~2초 | 3분 |
| HWP/PDF 파싱 | ~3초 | 5분 |
| LLM 자격요건 추출 | ~15~20초 | 25~35분 |
| 검증 + 정적 페이지 생성 | ~1초 | 2분 |
| | | **합계 40분 내외** |

> 💡 공고 첨부는 10~30페이지로 길다. 전량을 LLM에 넣으면 건당 40초까지 간다.
> **"지원대상 / 신청자격 / 지원내용" 섹션만 전처리로 추려서** 넣으면 2,000~4,000 토큰으로
> 줄어 건당 15~20초가 된다. 이 전처리가 비용의 절반을 좌우한다.

### 7-2. ★ 진짜 운영 부담은 건수가 아니다

처리량이 적은 것과 운영이 쉬운 것은 다르다. 실제 부담은 다음에서 온다.

| 부담 요인 | 내용 | 대응 |
|---|---|---|
| **공고 수정·연장** | 지원사업은 정정공고가 잦다. 마감 연장, 자격 변경, 예산 조정. **신규 처리보다 변경 추적이 더 까다롭다.** 놓치면 틀린 정보가 사이트에 남는다 | **공고 ID별 해시 저장 + 변경 감지(diff)를 처음부터 설계.** 나중에 붙이면 전면 재설계 |
| **양식 다양성** | 파싱 실패율은 건수가 아니라 **기관 수**에 비례. 100건이 10개 기관이면 양식 10종 | 신규 기관 유입 감지 + 양식별 성공률 추적 |
| **실패 큐 누적** | 100건 중 10% 실패 = 하루 10건. 일주일이면 70건 | 실패 큐 대시보드 + 원인 자동 분류 |
| **품질 드리프트** | 새 양식이 들어오면 추출 정확도가 **조용히** 떨어진다 | 정기 샘플 감사 |

### 7-3. 관리자 역할 LLM

위 부담을 사람이 매일 처리하면 서비스가 썩는다. LLM에게 **감시 레이어**를 맡긴다.

| 역할 | 산출 예시 |
|---|---|
| 파싱 실패 원인 분류 | "3건 스캔 PDF(OCR 필요), 5건 표 구조, 2건 암호화" |
| 추출 품질 자가 감사 | 신규 기관 양식 유입 시 정확도 하락 조기 경보 |
| 변경 공고 diff 요약 | "마감 3/15 → 3/29 연장, 매출요건 5억 → 10억 완화" |
| 일일 브리핑 | "신규 87건 / 처리 79 / 실패 8 / 사람 검토 필요 3" |

**이 레이어가 있으면 하루 10분 관리로 돌아가고, 없으면 조용히 썩는다.**
건수가 적어서 쉬운 게 아니라, 감시 레이어가 있어야 쉬워진다.

### 7-4. 초기 백필 전략

| 범위 | 건수(추정) | 사용자 가치 | SEO 가치 |
|---|---|---|---|
| **진행중 공고만** | 수백 건 | 높음 | 낮음 |
| + 최근 1~2년 마감분 | 수천 건 | 낮음 (이미 마감) | **높음** |

마감된 공고는 사용자에겐 쓸모없지만 **검색 유입에는 크다.**
"2025 청년창업사관학교 자격요건"으로 들어온 사용자가 2026 공고를 보게 된다.

**권장 순서: 진행중 공고로 시작 → 파이프라인 안정화 → 과거분 백필.**
처음부터 수천 건을 하면 정확도 관리 대상이 감당 안 된다.

## 8. 수익 모델

### 8-1. 애드센스 — 자릿수 계산

수익 = `PV × RPM ÷ 1000`

| 분야 | RPM (1000PV당) |
|---|---|
| 일반 블로그 | 500~2,000원 |
| **B2B·금융·컨설팅 계열** | **2,000~5,000원** |

지원사업 분야는 "사업계획서 대행", "정부지원사업 컨설팅" 등 고단가 키워드가 붙어 후자에 가깝다.
보수적으로 **RPM 2,000원** 가정 시:

| 목표 | 필요 월 PV | 일 PV |
|---|---|---|
| **월 3만원 (LLM 구독료 수준)** | 13,500 | **약 450** |
| 월 13만원 | 67,500 | 약 2,250 |
| 월 100만원 | 500,000 | 약 16,700 |

**일 450 PV는 현실적인 목표.** 공고 수천 건이 각각 색인되면 롱테일 검색으로 도달 가능하다.
정적 호스팅이라 **운영비가 0**이므로 수익이 그대로 순익이며, 적자 날 구조가 아니다.

> ⚠️ RPM 수치는 대략적 자릿수이며 분야·시기에 따라 크게 변동. 착수 후 실측 필요.

### 8-2. ★ 애드센스 승인이 1차 관문

트래픽보다 **승인**이 먼저다. 이걸 모르고 시작하는 경우가 많다.

구글 애드센스 정책은 **스크랩 콘텐츠 및 부가가치 없는 자동 생성 콘텐츠**를 금지한다.
공공 API 공고를 나열하고 LLM 요약만 붙인 사이트는 거부될 위험이 실재한다.

| 사이트 성격 | 판정 |
|---|---|
| 공고 복붙 + LLM 요약 나열 | ❌ 거부 위험 높음 |
| **자격요건 구조화 + 매칭 필터 + 원본에 없는 판단 정보** | ✅ 부가가치 인정 가능 |

즉 **자격요건 매칭은 차별화 요소이자 애드센스 승인의 근거**다.
착수 전 애드센스 정책 문서를 직접 읽을 것. 다 만들고 거부당하면 뼈아프다.

### 8-3. 수익 타임라인 — 6개월은 0원

SEO 유입은 색인·순위 상승에 **통상 3~6개월**이 걸린다.

```
1~2개월   개발 + 초기 백필              수익 0
3개월     배포 + 애드센스 신청           수익 0
4~6개월   색인·순위 상승                수익 몇천 원
6~12개월  안정화                        월 3만원 근처
```

### 8-4. 전체 수익 경로

| 모델 | 현실성 | 비고 |
|---|---|---|
| 애드센스 | 중 | 부수입 성격. 위 계산 참조 |
| **제휴 리드** | **상** | 사업계획서 대행·컨설팅·세무·노무 연결. **1건이 애드센스 몇 달치.** 단, 영업 근육 필요 |
| 프리미엄 알림 구독 | 중 | 경쟁 서비스가 이미 무료 제공 중 |
| B2B 데이터 판매 | 하 | 컨설팅사 대상. 영업 필요 |

**광고만으로 의미 있는 돈은 안 된다. 자릿수를 바꾸려면 제휴로 가야 한다.**
지원사업 사용자는 "지원해야겠다"까지 왔지만 **사업계획서를 못 쓴다.**
그 대행 건당 수십만~수백만원이 오가며, 리드 1건 단가가 광고 몇 달치다.

### 8-5. 냉정한 기대치 설정

개발 시간을 시급으로 환산하면 **사업으로선 형편없다.** 100시간 들여 월 3만원이다.

이 프로젝트의 실제 값어치는 다음이며, 광고 수익은 **"적어도 손해는 안 본다"는
심리적 방어선**으로 보는 것이 맞다.

- LLM 파이프라인 실전 경험 (수집 → 파싱 → 추출 → 검증 → 배포)
- 실제 운영되는 서비스 1개
- HWP 파싱이라는 진입장벽 있는 기술 자산

## 10. 법적 체크리스트 (사업화 전 필수)

- [ ] 공공데이터포털 각 API의 **이용약관 상 상업적 이용 범위** 확인
- [ ] 기업마당 API 이용 조건 및 **출처 표시 의무** 확인
- [ ] 첨부파일(HWP/PDF) **재배포 가능 여부** — 원문 링크만 제공하는 것이 안전
- [ ] 민간 소스 추가 시 각각 ToS · robots.txt 확인
- [ ] 사용자 프로필 수집 시 **개인정보처리방침** 필요 여부 (로컬 저장이면 회피 가능)
- [ ] 광고 게재 시 **통신판매업 신고** 해당 여부
- [ ] **면책 조항** 작성
- [ ] ⚠️ **변호사 검토** — 사업화 결정 시 가장 비용 대비 효과가 큰 투자

> 참고: 취미 프로젝트일 때와 **사업자 명의로 수익화하는 순간 법적 취급이 달라진다.**

## 11. 로드맵

각 단계에 **중단 기준**을 둔다. 통과 못 하면 다음으로 가지 않는다.

| 단계 | 내용 | 통과 기준 |
|---|---|---|
| **0** | 기업마당 API 실제 호출 → 서울·경기 필터링 → 건수·필드·**첨부 URL 제공 여부** 확인 | 첨부 URL이 나오는가? **안 나오면 기획 전면 재검토** |
| **1** | HWP/PDF 파싱 PoC — 공고 20건 손으로 검증 | 파싱 성공률 80%↑ |
| **2** | LLM 자격요건 추출 — 20건 정답 직접 작성 후 대조 | 핵심 필드 정확도 95%↑ |
| **3** | 정적 사이트 MVP (목록 + 필터 + 상세 + 마감 캘린더) | 본인이 실제로 쓰게 되는가 |
| **4** | 사용자 5명 인터뷰 | "이거 쓰겠다"가 3명↑ |
| **5** | SEO 최적화 + 공고별 정적 페이지 생성 | 검색 색인 등록 |
| **6** | 광고 게재 → 수익 실측 | 실제 RPM 확인 |
| **7** | 전국 확대 / 사업자 등록 | 재방문 사용자 확보 후 |

**0단계가 관문이다.** 첨부파일 URL을 API가 안 주면 차별화 전략 자체가 성립하지 않는다.
반나절이면 확인 가능하므로 **가장 먼저 할 것.**

## 13. 리스크

| 리스크 | 영향 | 대응 |
|---|---|---|
| **API가 첨부 URL을 제공하지 않음** | 치명적 — 차별화 불가 | **0단계에서 최우선 확인** |
| HWP 파싱 실패율 높음 | 높음 | HWPX 우선 지원, 실패 건은 "원문 확인" 처리 |
| **LLM 환각 → 잘못된 마감일·자격** | **치명적** | §6 정확도 원칙 엄수. 핵심 사실은 API 원본만 |
| 트래픽 확보 실패 | 높음 | SEO 중심 설계. 4단계에서 조기 검증 |
| 경쟁사가 같은 기능 추가 | 중간 | HWP 파싱 품질이 해자 |
| 공공 API 정책 변경 | 중간 | 복수 소스 확보 |
| 민간 소스 법적 분쟁 | 중간 | 공공 API 우선, 민간은 최소화 |

### Jetson의 역할 — 개발용에 한정

⚠️ **Jetson으로 서비스를 운영하면 안 된다.**
- 집 정전·인터넷 장애 = 서비스 중단
- 하드웨어 고장 시 대체 불가
- 고객 발생 시 SLA 요구

**Jetson은 프로토타입·실험 장비**로 쓰고, 운영은 클라우드로 간다.
정적 사이트 + 배치 처리 구조라 클라우드 비용도 미미하다.

## 15. 결론

**job-radar보다 사업성이 명확히 높다.**

- 법적 리스크 낮음 (공공데이터)
- 데이터 획득 쉬움 (공식 API, 크롤러 불필요)
- 사용자 동기 강함 (지원금이 걸려 있음)
- 수익화 경로 넓음 (광고 + 제휴 리드)
- 정적 아키텍처가 광고 모델(SEO)과 정합

**단, 성패는 두 가지에 달려 있다.**
1. **첨부파일에서 자격요건을 정확히 뽑아낼 수 있는가** (기술)
2. **틀린 정보를 내보내지 않을 수 있는가** (신뢰)

두 번째가 더 중요하다. 마감일 하나 틀리면 서비스 신뢰가 끝난다.
**"모르면 비워둔다"는 원칙을 처음부터 코드로 강제할 것.**
